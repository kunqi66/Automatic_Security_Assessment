# `resource_metrics` 永远没有数据 —— 一份还没修的诊断

> 这是一份**诊断**，不是一份修复记录。结论是这张表在任何情况下都写不进数据，
> 原因是 B2 与 B3 对「容器活多久」的理解不一致。**代码没动**，
> 因为修它要在两份模块设计之间做一个选择，不该由实现顺手决定。

## 现象

跑完 `tools/e2e.py usercenter`（`assessment #14`，五个阶段全部 `completed`）之后：

```
GET /api/v1/assessments/14/metrics  ->  200  []
```

前端对应的是工作台左栏的「沙箱资源占用」卡片
（`frontend/src/modules/pipeline/ResourceMetrics.tsx`），
它拿不到采样点，于是显示空状态「尚未产生资源采样」—— **不崩，但永远是空的**。

直接查库确认不是接口的问题：

```sql
SELECT COUNT(*) FROM resource_metrics;   -- 0
```

**所有 14 次评估、全部 0 行。** 不是这一轮跑漏了，是从来没写进去过。

## 这不是"忘了接线"，是接不上

先把看起来像的原因排除掉。这条链路上每个零件都在：

| 零件 | 位置 | 状态 |
|---|---|---|
| 表 + 模型 | `app/models/observability.py::ResourceMetric` | ✅ 有，迁移里有 |
| 采样器实现 | `app/orchestrator/metrics.py::MetricsSampler` | ✅ 165 行，含差分算 CPU |
| 采样间隔配置 | `settings.metrics_sample_interval_seconds` | ✅ 有 |
| 构造与停止 | `app/orchestrator/engine.py:262` 构造，`finally` 里 `stop()` | ✅ 都调了 |
| 查询接口 | `GET /assessments/{id}/metrics` | ✅ 200 |
| 前端图表 | `ResourceMetrics.tsx` | ✅ ECharts 双轴 |

**缺的是 `MetricsSampler.start()` 的调用者。** 全仓库只有定义，没有调用点：

```bash
grep -rn "metrics.start" backend/app/     # 无输出
```

到这里看起来像是"漏了一行"。但补上那一行会立刻暴露真正的问题：

```python
async def start(self, *, assessment_id: int, stage: StageName, container_id: str) -> None:
```

它要一个**在采样期间持续存在的 `container_id`**。而实现里没有这样的东西。

## 根因：容器的寿命，两边理解不同

**B3 的设计假设容器是长驻的。** `B3-多Agent编排引擎.md` §2：

> 资源指标采集 | 阶段运行期调用 B2 采样容器 CPU/内存，落 `resource_metrics` 并推送

§4 写得更明确：**「阶段运行期按间隔调 `SandboxExecutor.metrics()`」**，
§7 定了 **5s 采样、30 天 TTL**。"按间隔"三个字预设了容器在阶段内一直活着。
B2 的设计也是这么想的 —— `B2-沙箱隔离模块.md` §3.1 提到 `_HandleRegistry`、
"保活 = `restart_policy=no` + handle 存活即活跃"，都是一副长驻容器的样子。

**实现里容器是一次性的。** `app/sandbox/service.py::run_once()`：

```
建容器 → 启动 → 等结束（超时强杀）→ 收集输出 → **无论成败都删容器**
```

`container_id` 只在这个方法内部活着 —— 它被塞进服务私有的 `self._active` 集合，
方法返回前就从 `finally` 里删掉了。调用方（`verify/runner.py:481`）
拿到的是 `ExecResult`，**里面没有容器 id**，而且拿到的时候容器已经没了。

所以 `MetricsSampler.start(container_id=...)` 这个签名在当前实现下
**没有任何合法的实参可传**。这不是接线疏漏，是两条契约对不上。

> 顺带说明了另一件事：`run_once` 的一次性语义是**有意的**、而且是对的 ——
> `probe.py:1225` 那段注释解释了为什么"一次容器跑完一个 Finding 的全部探针"
> （容器启动成本远高于 HTTP 往返，2 vCPU 上不能一探针一容器）。
> 问题不在 `run_once`，在于**资源采样这个需求从来没被折进它的设计里**。

## 两个修法，我倾向后一个

### 甲：让 B2 暴露"当前活跃的容器"

`SandboxService` 已经有 `self._active` 这个集合了 —— 它本来就是为了
「知道现在有哪些容器在跑」而存在的。加一个只读的
`active_containers() -> tuple[str, ...]`，把 `MetricsSampler` 的
`start(container_id=...)` 改成 `start()` 后**轮询**：

```python
for cid in await self._sandbox.active_containers():
    cpu, mem = await self._sandbox.stats(cid)
```

- **好处**：不动 `run_once` 的语义，不动探针那条已验证的路径；
  `_active` 已经是既成事实，只是从私有变成契约。
- **代价**：要改 `Sandbox` 这个 Protocol（`sandbox/ports.py`），
  以及"契约 1"那份文档；采样点变成"这一轮有哪些容器"，而不是"这个阶段的容器"。

### 乙：采样挪进 `run_once`，由 B2 自己写表

`run_once` 等容器结束的那段（`_wait_for_exit`）本来就是轮询，
在那里按间隔取 `stats()` 并写 `resource_metrics`。

- **好处**：容器 id 天然在手，不需要新契约；采样点最准（真的在容器活着时采）。
- **代价**：**B2 要写数据库** —— 而 B2 现在的定位是"不碰业务库"，
  `models/observability.py` 的 docstring 还写着「只有 B2 写这张表」
  （已被 B3 设计 §5.1 推翻，注释本身是旧账）。这会把 B2 从纯执行器
  变成有状态组件，是比甲更大的定位改动。

**我倾向甲**：它只把已经存在的 `_active` 提升为契约，不动 B2 的定位，
也不碰探针那条已经逐点验证过的路径。乙更"准"，但代价是模块边界。

### 都不做也行，但要如实说

如果决定不做，那至少**别让这个面板假装是待采集的** ——
现在它显示「尚未产生资源采样」，读起来像"再跑一会儿就有了"，
而实际上是**永远不会有**。这种情况应该是一句明确的
「该功能未接线（见 `docs/资源采样为什么是空的.md`）」。
**一个永远空着的图表，比一个说明白的缺口更糟** ——
它让人以为数据在来的路上。

## 为什么值得留着这条记录

这个缺口不是"没写完"，是**两份设计文档都写完了、代码也都写了、却对不上**：

- B3 说"按间隔采样容器"，B2 说"容器保活"，实现说"用完就删"；
- 三边单独看都自洽，合起来永远采不到一个点；
- 而且它有完整的表象（表、模型、接口、图表、配置项），
  **看起来像"数据还没攒够"，不像"坏了"**。

这正好是 `CLAUDE.md` 里那条纪律的反面教材：
**跨模块契约要双向核**。B3 引用了 B2 的 `metrics()`，但没有核对
"B2 交付的容器生命周期，能不能支撑我的采样间隔"。
