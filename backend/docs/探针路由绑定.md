# 探针路由绑定：把「同类漏洞存在」与「这一行被跑通」分开

> 本文对应 `app/verify/routes.py`、`app/verify/context.py`，
> 以及 `app/verify/runner.py` 里那一个 `bound_to_finding` 分支。
>
> 结论先说：**这个问题被解决到 10/15，剩下 5 条是结构性的、且我选择不解决。**

---

## 1. 问题：15 条「已验证」里，10 条的验证发生在别的端点上

动态验证阶段的探针是**按漏洞类别**生成的模板，模板里的路由是**写死的**。
`sqli` 的两条模板，`url_path` 都是 `/search`。

于是同一台靶场上的三条 SQL 注入 finding —— 分别在 `/search`、
`/api/order/query`、`/admin/login` —— 各自跑了一遍**同一个** `/search` 探针，
各自命中，各自被记为 `verified`。

`poc_attempts` 表里留下的原始记录。下表**不是回忆出来的**，是拿修复后的
`bind_route` 反查每条 finding 真正的端点，再去比对修复前那次运行
（`assessments.id = 6`）**实际发出的请求路径**得到的：

| 漏洞 | 静态分析定位的位置 | 反查出的它自己的端点 | 探针实际打的 | 判定 |
|---|---|---|---|---|
| #48 | `app.py:88` | `GET /search?q` | `/search?q=…` | ✅ 逐点 |
| #50 | `app.py:153` | `POST /api/upload [body:file]` | `/api/upload` | ✅ 逐点 |
| #52 | `app.py:194` | `GET /api/ping?host` | `/api/ping?host=…` | ✅ 逐点 |
| #53 | `app.py:220` | `GET /api/file?path` | `/api/file?path=…` | ✅ 逐点 |
| #55 | `app.py:290` | `POST /api/deserialize [body:data]` | `/api/deserialize` | ✅ 逐点 |
| #46 | `admin_login.py:43` | `POST /admin/login [body:username]` | `/search?q=…` | ❌ **借道** |
| #47 | `admin_login.py:43` | `POST /admin/login [body:password]` | `/search?q=…` | ❌ **借道** |
| #49 | `app.py:114` | `GET /api/order/query?id` | `/search?q=…` | ❌ **借道** |
| #51 | `app.py:165` | `GET /uploads/{payload} [path:name]` | `/api/file?path=…` | ❌ **借道** |
| #54 | `app.py:241` | `GET /api/download?file` | `/api/file?path=…` | ❌ **借道** |
| #45, #56–59 | `admin_login.py:23`、`config.py:26/27/28/32` | —（无端点） | `/.env`、`/debug/config` | ❌ **未绑定** |

**逐点 5 / 借道 5 / 结构性未绑定 5 —— 也就是 15 条里有 10 条不是逐点跑出来的。**

报告里这 15 条印出来是同一句话：「已通过动态验证」。

### 为什么这不是"措辞不严谨"，而是结论强度被高估

「这一类漏洞在本目标上存在」和「你看到的这一行确实被跑通了」是**两个不同的命题**，
证据强度差一个量级：

- 前者支持「这台靶场有 SQL 注入」（一个关于**目标**的结论）；
- 后者支持「`admin_login.py:43` 这行拼接是活的注入点」（一个关于**这行代码**的结论）。

报告卖的是后者。而 15 条里只有 5 条真的做到了后者。

那 5 条 `hardcoded_secret` 尤其值得单独说：它们"通过"的方式是探针读到
靶场的 `/.env`。而 `/.env` 可读证明的是**「这台机器的配置文件暴露了」**，
它**没有**证明 `config.py:26` 那个常量被谁利用了 —— 两者之间隔着一整条攻击链。

### 更糟的一面：它同时制造了假阴性

同一个缺陷在另一个方向上更危险。`admin_login.py:43` 那两条 finding
（`username`、`password` 两个注入点各一条）在更早的一次运行里
（`assessments.id = 4`、`5`）被记为 `rejected` —— 「测了，不存在」。
而实际上探针从未打到 `/admin/login`：它打的是 `/search?q=`，
而 `/search` 的 SQL 是 numeric 两列语境，`username` 的注入点在**字符串**语境里。

**探针打错了地方 → 没命中 → 判据忠实地报告"无差异" → 落 `rejected`。**
三个环节每一步都没写错，结论是错的。一次假阳性会让人多查一次；
一次假阴性会让人**永远不去查**。

> **为什么同一段代码，`id=5` 判 `rejected`、`id=6` 判 `verified`？**
> 这两次运行的 `poc_attempts` 摆在一起就能看出来，而且答案是同一个根因的
> **第三种表现**：
>
> ```
> id=5 →  GET /search?check_login=1%20UNION%20SELECT…   ❌ 未命中
>         GET /search?username=1%20UNION%20SELECT…      ❌ 未命中
> id=6 →  GET /search?q=1%20UNION%20SELECT…             ✅ 命中
> ```
>
> `/search` 只读 `q` 这一个参数。`id=5` 那次把参数名推成了
> `check_login`（从污点路径的 propagate 步符号里取的）、`username`、`password`
> —— **三个都不存在**，载荷从头到尾没被应用读过，响应自然与基线逐字节相同。
> `id=6` 那次退回模板声明的规范参数名 `q`，于是"通过"了。
>
> 也就是说 `id=5` 的 `rejected` 完全建立在**一个错的参数名**上。
> 这正是 `param_is_canonical` 那条判据的由来：**推导出来的参数名只能用来
> 多试一次机会，不能用来下结论** —— 证伪要求的是「打穿了也没反应」，
> 而打在一个不存在的参数上，连"打"都算不上。
>
> 两次运行的差别只是参数名，结论却从"不存在"翻成"已验证"。
> 一个结论会因为与结论无关的细节在两个极端之间跳动，
> 说明它当时并不具备结论应有的稳定性。

## 2. 根因链：三层，缺一层都修不掉

要修这个问题，得连着过三关。任何一关不过，前面的工作都白做。

### 第一层：路由从哪来

finding 只告诉系统「`admin_login.py:43` 有个注入点」。
要把它变成一条真实请求，需要知道：**端点在哪个 URL、哪个 HTTP 方法、
参数叫什么、载荷放进 query 还是 body**。

这四样东西 finding 里一个都没有 —— 它们在**路由装饰器**上，不在污点路径上。

### 第二层：锚点选错就永远找不到

最自然的想法是「从 sink 那一步往上找路由」。**这个想法在靶场上直接失败**：

```
[source]      app.py:304          request.form.get("username", "")   ← 路由在这一层
[propagate]   app.py:306          check_login(username, password)
[propagate]   admin_login.py:29   def check_login(...)
[sink]        admin_login.py:43   cursor.execute("SELECT role ...")   ← sink 在这一层
```

`check_login()` 是一个**没有路由的辅助函数**，路由装饰器在 `app.py:301` 的
`admin_login()` 上。只看 sink 所在的文件，永远找不到那个装饰器。

→ 所以反查必须**锚在 source（请求侧那一步）**，而不是 sink。
`routes.py::bind_route` 按 `source → 其余步` 的顺序遍历，任一步落进
某个带路由装饰器的函数体内，绑定就成立。

### 第三层：路由对了，载荷未必进得去语法位置

这一层是修前两层时**新暴露出来的**，也是最容易被忽略的一层。

路由绑定成功之后，`1 AND 1=1` 会被真的投进 `/admin/login` 的 `username`。
但那条 SQL 是：

```sql
SELECT role FROM users WHERE username = '<输入>' AND password = '<输入>'
```

投进去变成：

```sql
... WHERE username = '1 AND 1=1' AND password = '...'
```

一条**语法完全合法、但恒假**的 SQL —— 因为那个 `1 AND 1=1` 落在引号**里面**，
是字符串内容，不是表达式。

结果：响应与基线一致 → 布尔差分判「无差异」→ 又一次落 `rejected`。

**换句话说，只做路由绑定会把一个假阳性换成一个假阴性。**
这正是为什么 `context.py` 不是"锦上添花"，而是这一层修复的必要组成部分。

## 3. 解决：三层，逐层落点

### ① 路由反查 —— `app/verify/routes.py`

纯函数 `bind_route(reader, finding) -> RouteBinding | None`。
对给定的 `reader` 是纯的，所以测试可以喂内存字符串，不必造目录树。

`RouteBinding` 字段全部是**反查出来的事实**：

| 字段 | 说明 |
|---|---|
| `url_path` | 探针要打的路由；含路径参数时被注的那一段写成 `{payload}` 占位 |
| `methods` | HTTP 方法元组 |
| `param_name` | 参数名，**可能是 `None`**（见下） |
| `local_var` | 承接输入的**局部变量名** |
| `inject_in` | 载荷放 query / body / header / path |
| `route_file` / `route_line` | 端点所在的文件与行 |
| `anchor_file` / `anchor_line` | 反查的锚点（source 步） |

两个实测踩出来的细节：

- **`param_name` 允许是 `None`。** 污点来源有时只记到通道 ——
  实测 `app.py:147` 的 snippet 就是光秃秃的 `request.files`，读不出字段名。
  这时用模板声明的 `default_param` 补上。**路由是对的，补的只是字段名** ——
  这个区别在报告里要能看出来，所以 `Probe` 上有 `param_is_canonical`。
- **`param_name` 与 `local_var` 常常不同名。** `/api/order/query` 的 HTTP 参数
  叫 `id`，局部变量叫 `order_id`，而 SQL 拼接链上出现的是后者。
  少了 `local_var`，`context.py` 就认不出注入点是哪个操作数。

### ② 注入上下文匹配 —— `app/verify/context.py`

从 sink 那一行往上认：这个局部变量被拼进了哪个 SQL 的哪个位置。

`infer_sink_context()` 返回：

- `kind`：`STRING`（拼接处引号未闭合）或 `NUMERIC`；
- `columns`：`SELECT ... FROM` 之间在引号深度 0 上的逗号数 + 1；
- `sql_prefix`：**该变量之前所有字符串字面量的拼接**。

`payload_fits_context(technique, payload, ctx)` 据此判断：

- `UNION_EXTRACT` 要求 `NUMERIC` **且** `ctx.columns == payload 自己的列数`；
- `BOOLEAN_BLIND` 要求 `NUMERIC`；
- 其余技术不额外限制。

**`sql_prefix` 必须是"累计所有字面量"，不能只看紧邻的那一个。**
这是实测出来的：`password` 的拼接链是

```python
"... username = '" + username + "' AND password = '" + password + "'"
```

紧邻 `password` 的那个字面量是 `"' AND password = '"`，里面有 **2** 个引号
→ 偶数 → 判成 `NUMERIC`（**错**）。
累计它前面**所有**字面量，`"... username = '"` 贡献第 3 个引号 → 奇数 → `STRING`（**对**）。

> 这里还有个过程中的教训值得记：`infer_sink_context` 的第一版是**正则**写的，
> 而且写错了 —— 贪婪匹配吞掉了整个调用表达式，还把 `username` 判成了
> `numeric`。**一个用来防止"载荷进错语法位置"的模块，自己犯了同一类错。**
> 后来整段重写在 AST 上（`_flatten_concat` + `_enclosing_sink_call`），
> 才和 `routes.py` 用的是同一层事实。

### ③ 结论闸门 —— `fingerprints.py::_is_conclusive` + `runner.py`

两处收紧：

**(a) 没有否证力的探针不参与证伪表决。** `_is_conclusive` 加了第二个前置条件：

```python
if not probe.param_is_canonical:
    return False
if not probe.payload_fits_context:
    return False
```

理由与原有的 `param_is_canonical` 判据是同一条：
**「载荷没进入语法位置」与「注入不存在」在响应里长得一模一样。**
分不清这两者的证据，没有资格投反对票。

**(b) 命中但未绑定，只能落 `potential`。** `runner.py` 里新增的分支：

```python
if matched is not None and not matched[0].bound_to_finding:
    return VerificationResult(
        verdict=Verdict.UNVERIFIED,
        status=VulnStatus.POTENTIAL,
        cvss_after=cvss_before,          # ← 不给 CVSS 加分
        unverified_reason="动态探针命中了，但打在**该类漏洞的标准形态路由**上…",
    )
```

这条改动让 `verified` 的语义变了，是整次修复里**影响最大**的一处 ——
见下一节。

## 4. 语义变化：`verified` 变难拿了，而这是重点

改动之后：

```
verified  ⟺  探针命中  ∧  探针打在本条 finding 自己的端点上
```

带来的直接后果：**5 条 `hardcoded_secret` 从 `verified` 掉到 `potential`。**

它们原先"通过"的方式是：探针去读靶场的 `/.env`，读到了，于是判定通过。
但 `/.env` 可读证明的是**「这台机器的配置文件暴露在公网」**——
它**没有**证明 `config.py:26` 那个常量被谁利用了。这两件事之间隔着一整条攻击链。

这是**故意的**取舍：

- 报告里 `verified` 变少，看起来"能力变弱了"；
- 换来的是 `verified` 这三个字可信 —— 它现在意味着
  「这一行所在的端点被真的跑通了」。

**宁可 `verified` 少，不可 `verified` 假。** 前者是能力边界，
后者是报告失去意义。一个安全评估报告如果会在关键结论上高估，
那它剩下的部分也没人敢信了。

顺带：`bound_to_finding` **没有**新增数据库列，是从
`status == verified` 推出来的 —— 因为上面的等价关系成立，再存一份就是冗余；
而且 `poc_attempts` 加列要先改 PRD §6（本项目列名 SSOT）。
报告里那两句话（`partials/vuln_card.j2`、`partials/md_vuln.j2`）
按这个字段分成两种写法：
**逐点确认** 与 **仅类别级**，不再是一句万能的免责声明。

## 5. 没解决的部分：白名单就是覆盖率上限

这是整件事里最该讲清楚的一段。

### `/admin/login` 在**任何**绑定质量下都无法逐点验证

`/admin/login` 的注入点在**字符串**语境里，而能打穿它的载荷长这样：

```sql
' OR '1'='1' --          -- 需要尾部注释吞掉后面的 ' AND password = '...'
' UNION SELECT 'N' --    -- 1 列，且同样需要尾部注释
```

它们**全部过不了载荷闸门**。闸门是形态白名单，每条都刻意写得窄
（`app/verify/guard.py`）：

```python
_RE_UNION   = re.compile(
    r"^\s*[0-9A-Za-z_\-']{0,64}\s+UNION\s+SELECT\s+'(?:[A-Za-z0-9_]{1,64}|\{N\})'\s*,\s*"
    r"'[A-Za-z0-9_]{1,64}'\s*(--\s*)?$", re.IGNORECASE)
_RE_BOOLEAN = re.compile(r"^\s*[0-9A-Za-z_\-']{0,64}\s+AND\s+1\s*=\s*[12]\s*$", re.IGNORECASE)
```

两个**互相独立**的原因，任何一个都足以否掉：

1. **`_RE_UNION` 把列数钉死在 2。** 它要求 `SELECT 'x', 'y'` 恰好两列 ——
   这是为了和靶场 SQLite 的列数对齐（PRD §10.1），代价是
   `SELECT role FROM users`（1 列）与 `SELECT id,name,price`（3 列）都打不了。
2. **`_RE_BOOLEAN` 不允许尾部注释。** 它以 `1=1|1=2` 紧接 `\s*$` 结束，
   后面不能跟 `--`。而字符串语境里**没有注释就闭合不了那个引号** ——
   `username = '' AND 1=1' AND password = 'x'` 是一条语法错误的 SQL。

注意 `_RE_BOOLEAN` 的字符类里**是**允许前导 `'` 的，所以 `' AND 1=1`
能过闸门 —— 但它过不了 SQL 解析，因为拼出来语法就不对。
**"过了闸门"和"能打穿"是两件事**，这一层差异正是 `payload_fits_context`
存在的原因：它让系统在**发请求之前**就知道这条探针不可能有结论，
而不是发出去、没命中、然后错误地据此否证。

### 为什么不放宽白名单

因为闸门是一道**安全边界**，不是覆盖率旋钮。它保证的是
「探针绝不会发出有副作用的载荷」，而它之所以可信，
正是因为它是**封闭白名单**——不是"过滤危险字符"那种可以绕的启发式。

放宽到能覆盖 `/admin/login`，等于把 `--` 注释、`OR` 逻辑运算、
任意列数的 `UNION` 都放进白名单。那时闸门就从
「这几条载荷是我逐条审过的」退化成「这些**形状**大概没问题」——
而后者正是所有载荷过滤方案失效的方式。

**所以我选择不放宽，并把这条边界写进报告和文档。**
一个诚实的能力边界，比一个悄悄降低安全标准的覆盖率数字有价值。

### 同类边界：结构上无法逐点的 finding

`hardcoded_secret` 永远绑不上端点 —— 它的污点路径里**没有请求侧那一步**，
`bind_route` 正确地返回 `None`。这不是缺陷，是这类漏洞的性质：
它不是一个"端点可触发"的漏洞。

### 一个顺手修掉的沉默缺陷：`InjectIn.PATH` 曾是空操作

`_inject()` 会为路径注入算出载荷，但 `_request()` **从来没有把它替换进 URL**。
于是路径参数类 finding（`/uploads/<path:name>`、`/api/user/<user_id>/profile`）
的探针**带着干净的 URL**发出去，回来当然不命中，然后被记为 `rejected`。

这类缺陷最坏的地方是它**不报错**：探针发了、响应回来了、
判据也正常工作了 —— 只是测的不是那件事。现在 `_request()` 会真的替换
`{payload}` 占位符（并用 `quote(payload, safe="/.")` 编码）。

## 6. 修复后的靶场实测

同一台 `ranges/ecommerce`、同一份源码、同一条流水线。

### 借道归零

| | 修复前（`assessment #6`） | 修复后（`assessment #7`） |
|---|---|---|
| 探针命中在本条**自己**的端点上 | 5 | **8** |
| 探针命中在**别的**端点上（借道） | 5 | **0** |
| 结构性无法绑定（`hardcoded_secret`） | 5 | 5 |

**借道从 5 条降到 0 条。** 新绑上的 3 条：

- `app.py:114` → `GET /api/order/query?id=` —— 走 `BOOLEAN_BLIND`
  （该 SQL 是 numeric **三**列，`_RE_UNION` 的 2 列形状用不了，
  `context.py` 正确地只放了布尔探针过去）；
- `app.py:165` → `GET /uploads/../../../../etc/passwd` —— 路径参数注入，
  以前 `InjectIn.PATH` 是空操作，探针**带着干净 URL** 发出去、必然不命中；
- `app.py:241` → `GET /api/download?file=…` —— 同一类。

### 状态分布：15 → 8 verified / 7 potential

```
修复前：  verified 15    rejected 0    potential 0     ← 15/15
修复后：  verified  8    rejected 0    potential 7
```

7 条 `potential` 的成分，一条不多一条不少：

| 条数 | 是什么 | 为什么是 potential |
|---|---|---|
| 5 | `hardcoded_secret`（`config.py:26/27/28/32`、`admin_login.py:23`） | 污点路径里没有请求侧那一步，`bind_route` 正确地返回 `None` —— **结构性**，不是缺陷 |
| 2 | `admin_login.py:43` 的 `username` / `password` | 绑定**成功**了（`POST /admin/login`），但字符串语境所需的载荷形态过不了白名单闸门 —— **安全取舍**，见 §5 |

关键是：**没有一条是 `rejected`。**
系统没有把"没能逐点验证"包装成"验证通过"，也没有把它误判成"漏洞不存在"。
两条 `/admin/login` 的 SQL 注入在靶场里是**真实存在**的，
静态结论原样保留，只是动态证据不足以支撑"逐点确认"。

### 一个副作用值得单独说

那 5 条 `hardcoded_secret` 从 `verified` 掉下来之后，**攻击链也变了**（5 条 → 4 条）。

这是对的：链规则只能由 `verified` 的节点驱动（`CHAIN_ELIGIBLE_STATUSES`）。
原先有链经过了"硬编码密钥"节点，而那个节点的"验证"来自读 `/.env` ——
**一条建立在借道证据上的攻击链，被当成推演的前提。**
现在它不再具备这个资格。链条变短了，但每一环都站得住。

> 想反过来验证这一点也很简单：把 `bound_to_finding` 的判据撤掉
> （即恢复"命中即 verified"），链会重新变回 5 条。**多出来的那条链，
> 就是借道证据凭空造出来的。**

### 一个附带发现

`/admin/login` 那两条在更早的运行里（`assessment #4/#5`）是 `rejected`。
现在它们稳定地停在 `potential` —— 这个位置才是对的：
**"没能确认" ≠ "确认不存在"**。修复前它们在两个极端之间跳，
取决于一个与结论无关的细节（探针参数名恰好撞对没撞对，见 §1）。

## 7. 第二个靶场把修复本身证伪了一次：IDOR 是绑定的反例

上面那一整套（反查端点 → 整体替换模板里那几个写死的值）在 `ranges/ecommerce`
上借道归零。换到 `ranges/usercenter`，**它把一条本来能验证的漏洞弄成了验证不了**。

第一次跑（`assessment #8`）：

```
[idor]             app.py:88    potential     ← 反查**成功了**，探针也发了，却落 potential
[hardcoded_secret] settings.py:14 potential   ← 这三条是结构性的（§5 已解释）
[hardcoded_secret] settings.py:15 potential
[hardcoded_secret] settings.py:16 potential
状态分布：{'potential': 4}    利用链 0 条
```

日志里绑定是成功的：

```
漏洞 75 已绑定到自己的端点：GET /api/user/{payload}/profile（参数 user_id，位置 path）
开始验证漏洞 75（idor）：计划 1 条探针，裁剪 0 条
```

**绑对了，还是没验证出来。** 而且失败长得很像"目标没有这个接口"：

| | 探针实际发的 | 为什么错 |
|---|---|---|
| ① 写入侧 URL | `POST /api/user/<nonce>/profile` | 这个路由**只收 GET** → 404 |
| ② 写入侧参数名 | `user_id=<nonce>` | 写入接口要的是 `nickname` |
| ③ 读侧 URL | `/api/user/2/profile` | 就算前两条对了，这串 URL 仍来自**模板**，命中只算类别级 |

三个错**各不相同**，而且是同一个决定造成的：**"绑定成功就把四个字段一起换掉"**。

这个决定在 ecommerce 上是对的 —— 那 15 条全是"一条请求、一个注入点"。
但 IDOR 的探针要发**两条打在不同端点上的**请求：

```
① POST /api/user/profile      写一条自造标记（这是**另一个**端点，不是 finding 所在的那个）
② GET  /api/user/2/profile    去读**别人**的资源（这才是 finding 自己的端点）
```

绑定只反查出**一个**端点 —— finding 的污点参数被用在哪个路由上，也就是 ②。
把它套到 ① 上，等于用"读接口的路由"去发"写接口的请求"。
`binds_route=False` 修的就是这件事：**一条绑定只描述一个注入点，
而多请求探针里有的请求根本不打在那个注入点上。**

② 那一格更隐蔽：`param_name` 原本无条件取 `cand.param_name`，而它是从
**finding 的污点路径**推出来的 —— 这里推成了 `user_id`（读接口的路径形参）。
可写入接口要的是 `nickname`，于是 `UPDATE users SET nickname = ?` 把昵称置成空串，
第二步当然读不到 nonce。**路由不由模板定，参数名就得由模板定**，是同一个理由。

"修复前它能验证"这句话是可复现的，不是推测。未绑定时 `_candidates` 给的候选
参数表由**模板默认名打头**：

```
[nickname, user_id]     ← 未绑定分支：`[template.default_param] + 推导值`
```

第一条就是 `nickname`，于是**碰巧打对了**。而绑定成功后候选集按设计
**塌缩成"每个模板一条"**（`param_name=binding.param_name or template.default_param`），
`nickname` 这一条随之消失，剩下的是 `binding.param_name` —— **读**接口的 `user_id`。

所以这次退化不是"绑定算错了"，而是：**为了消除"猜参数名"而做的那次塌缩，
在双请求探针上把唯一的正确解也一起消掉了。** 修法是给模板一个显式的
"我这条请求不由你接管"的开关，而不是把塌缩撤销 —— 塌缩本身是对的。

修完之后（`assessment #12`）：

```
[verified ] idor             app.py:88    严重度=high    ← 从 medium 升到 high
[potential] hardcoded_secret settings.py:14
[potential] hardcoded_secret settings.py:15
[potential] hardcoded_secret settings.py:16
状态分布：{'verified': 1, 'potential': 3}    利用链 1 条
```

落库的证据是实的 —— 匿名写、匿名读，读回自己写的标记。
`poc_attempts` 里那两条请求与**判定所依据的那条响应**（`response_raw` 存的是
判定请求的响应体，不是写入请求的）：

```
POST /api/user/profile     nickname=asaasa9923b038e5fe
GET  /api/user/2/profile   → {"nickname":"asaasa9923b038e5fe","ok":true,"user_id":"2"}
matched=1  http=200  guard=1
```

读回来的正是写进去的那个 nonce，而且 `user_id` 是 `2` —— 调用方从头到尾没有身份。

### 读侧为什么要"半绑"

写入侧必须由模板给死，读侧却**应该**从反查出的路由生成 —— 两边态度相反，
这不是别扭，是两条请求的性质不同：② 打的正是这条 finding 的端点，
让它照抄模板里写死的 `/api/user/2/profile`，就退回了 §1 那个老问题
（命中证明"这一类在本目标上成立"）。所以模板声明了 `aux_resource_id="2"`：
**路由从源码反查，id 由模板给**，两者拼起来才是读侧 URL。

实测这条派生是真的在派生，不是恰好同值：把路由换成 `/member/<uid>/view`，
探针读侧就变成 `/member/2/view`（`tests/test_verify_binding.py` 里钉了这条）。

id 为什么是常量 `2`：IDOR 的判定必须去读一个**不属于调用者**的资源，
而"具体是哪个 id"对判定没有影响（只要它存在）。固定成 `2` 是为了确定性。
**代价要说清楚**：它假定目标至少有 2 号用户。不成立时探针不命中、
落回"没能确认" —— 是漏测，不是误报，但这个边界是真的。

还有一个守卫：只有当**反查出的路由里真有载荷占位**时才做这个替换。
占位不在路由里（污点参数在请求体里）替换就是空操作，
会把读侧 URL 变成"这条 finding 自己的端点"（一个写入端点）——
**比模板原值还错**。这时退回 `aux_path`，且**不**声称逐点。

### 顺带修掉的一句假话

usercenter 那份报告里，链的入口节点写着：

> `app.py` 的 `idor` 已在沙箱中**无害验证**（**只读探针**命中特征），是整条链的起点。

**"只读"是假的。** IDOR 的探针要 `POST` 写一条标记，上传探针要 `POST` 传一个文件。
这句话是 `chain/builder.py::_entry_detail` 里对所有类别通用的一句模板文案
（`app/chain/builder.py:463`）。真正对**所有**探针都成立、而且更强的是闸门那条不变量：
**无破坏性** —— 不改真实数据、不外连、不落可执行文件。改成这一条之后，
它在每个类别上都是真话。**这是被第二个靶场逼出来的：换个类别跑一遍，
通用文案里的假话自己就浮出来了。**

### 这一段真正的产出

> **绑定不是"越绑越好"。** `bound_to_finding` 的判据是
> 「命中的那条请求打的是不是本条自己的端点」，
> 而不是「我们有没有成功反查出这条 finding 的端点」。
> 前者是**证据的属性**，后者是**我们的能力**。把两者混为一谈，
> 就会在"反查成功但请求打错了地方"时给出一个更自信、也更错的结论。

## 8. 设计原则（这部分是这次修复真正的产出）

1. **不变量比字段可靠。** `bound_to_finding` 没有落库，
   因为 `verified ⟺ 逐点确认` 这条不变量成立。多存一份就多一个会漂移的地方。

2. **判据的否决权要与其证据强度匹配。** 一个探针能不能投"证伪"票，
   取决于它的载荷有没有真的进入语法位置 —— 而不取决于它跑没跑。
   `param_is_canonical` 和 `payload_fits_context` 是同一个原则的两次应用。

3. **宁可少说，不可说满。** 报告里 `verified` 的减少是**功能**，不是**退化**。

4. **边界要写进产物里，不能只写在脑子里。**
   `/admin/login` 打不了这件事，写在本文、写在 `ranges/README.md`、
   也会印在报告里。用户拿到一份报告，应该能知道哪些结论强、哪些弱。

5. **LLM 不参与判定。** 整条修复里没有任何一处让模型判断
   "这个载荷行不行"。绑定是 AST 反查、上下文是 AST 推断、
   闸门是正则白名单 —— 全是可复现的确定性代码。
   把 LLM 拿掉，本文所有结论一字不变。

## 10. 已知的、尚未处理的

> 本节按时间顺序长出来，所以**下面保留了几条已经解决的**，并标了怎么解决的。
> 留着的理由是：这几条当初的判断里有对的部分也有错的部分，
> 后面的人（和面试官）看到的应该是完整的判断过程，不是一份整洁的结论。

### 10.1 ✅ 已解决：`unauth_access`（V6）没有静态规则

补上了 `patterns.detect_unauth_access`。**R7 从"不可达的死代码"变成了
"可达但没被跑到"** —— 它要 `unauth_access` **加** `file_upload` 同时出现在
一个目标上，而两个靶场各只有其中一个（ecommerce 有上传没未授权口，
usercenter 有未授权口没上传）。这不是缺陷，是靶场选型的结果。

**要证明 R7 本身是对的，正确做法是写一条链规则单测**（造一对 finding
喂给规则，断言产出链节点），而不是指望靶场恰好凑齐。
这条还没写 —— 它是"没想到"和"做不到"之间的第三种状态：**做得到，但没做**。

### 10.2 ✅ 已解决：`_RE_UNION` 的列数硬编码

载荷不再写死两列：`probe._build_union_payload(nonce, ctx.columns)`，
列数由 `context._column_count()` 从**该 finding 自己的 SQL 源码**里数出来
（`SELECT` 与 `FROM` 之间的顶层逗号 +1）。闸门同步从"恰好 2 列"放宽到
"1–16 列"，**字符集一个都没放宽**（见 `guard._RE_UNION` 的注释与
`test_union_widening_still_rejects_dangerous_shapes` 的 8 条恶意载荷）。

实测（`ranges/ecommerce/app.py:114`，三列 SELECT）：

| 载荷 | 结果 |
|---|---|
| 模板原值（两列） | HTTP 500，nonce 不在响应里 |
| 按列数构造（三列） | HTTP 200，nonce 在响应里 |

**但要说清楚它没有改什么**：`app.py:114` 在改动前后**都是 `verified`** ——
因为同类别下 `boolean_blind`（`1 AND 1=1`，与列数无关）那条探针一直在命中。
`assessment #11` 与 `#13` 的 15 条 finding 状态**逐条完全相同**。
所以这是**技术可用性**的修复，不是漏报的修复。把它讲成后者是不诚实的。

**顺带修掉的一个更危险的东西**：`_column_count` 对 `SELECT *` 曾返回 1。
以前这不出事（载荷恒为 2 列，`2 ≠ 1` 侥幸躲过），但载荷一旦按列数构造，
`1 == 1` 就会让"列宽未知的表上一次未命中"被当成**证伪** ——
把真注入写成 `rejected`。现在 `SELECT *`（及 `t.*`）显式返回 `None`
表示**不可知**，退回模板形态。有单测钉住。

**仍未处理的**：闸门上限是 16 列。超过 16 列的目标上 UNION 探针**必然
打不中**，且打不中的样子和"没有注入"一样。上限存在的理由是白名单必须
有限（§5），所以这不是 bug 而是取舍 —— 但它是**安静的**，这一条不好。

### 10.3 ❗ 未处理：未鉴权端点绑不上，V6 的动态证据只能到"仅类别级"

`assessment #14`（usercenter）实测：V6 的探针**命中了**
（`GET /api/user/list` → `matched=1 http=200`），但最终状态是
**`potential` 而不是 `verified`**。

原因在绑定，不在探针：`bind_route` 要从污点路径反查出"载荷该放进哪个参数"，
而未鉴权端点**根本没有输入参数** —— `list_users()` 不读 `request.*`，
`_param_and_inject` 逐条判据都不成立，于是返回 `None`，
绑定按设计拒绝（§5：它宁可"不绑定"也不猜一个参数名）。
`bound_to_finding=False` ⇒ 命中只能算**这一类**在本目标上成立。

**探针为什么还是命中了**：`unauth_probe` 模板里的路由恰好就是
`/api/user/list`（因为这个规则和这个靶场是一起写的）。换个路由名不同的
目标，这条探针会**打空** —— 这正是"模板写死了靶场路由"那个老问题的
残留，只是这次它藏在"已命中"的表象下面。

**怎么修（还没做）**：`bind_route` 已经能定位到端点
（日志里的"已定位端点 … 但无法从污点来源确定注入位置，不绑定"就是这里），
缺的只是"这条 finding 的技术**不需要**注入位置"这个知识。
把它加到调用方（`runner.py` 知道技术，`routes.py` 不知道 ——
保持 `routes.py` 与技术无关是对的）：
命中 + 端点已定位 + 技术无载荷 ⇒ 允许以 `param_name=None` 绑定。
这样既能把状态推到 `verified`，**又能顺手把探针 URL 从模板常量换成
finding 自己的路由**，一举两个问题。
本轮没做，因为它要动的是决定"载荷往哪发"的那段代码。

### 10.4 ❗ 未处理：`/api/download?file=` 返回空体

同类 `/api/file?path=` 正常。未定位，不影响任何结论（探针靠"路径参数注入"
那条路已经逐点验证了 `app.py:241`）。

### 10.5 值得做但没做：IDOR 的读侧 id 是模板常量 `2`

**这一条现在从"做不到"变成了"做得到"** —— §10.1 补上 V6 规则之后，
usercenter 的 `GET /api/user/list` 会作为一条 finding 出现，
而它正好可以用来**枚举出真实存在的资源 id**：先匿名取列表拿到 id 集合，
再挑一个不属于当前身份的 id 去读。

现在的写法（假定 `2` 号用户存在）不成立时是**漏测而不是误报**，
但它是真边界，而且它和 §10.3 是**同一个缺口的两面**：
两处都需要"这条 finding 能自己指出打哪里"。

### 10.6 多请求探针的"哪一条算证据"没有显式声明

现在靠 `bound_to_finding` 一个布尔位表达，而 IDOR 是"主请求打 A、判定请求打 B"。
探针数量再多一种（比如要三步的链式探针），这个位就表达不了了 ——
那时应该改成"每条子请求各自标注它打的是谁的端点"。
