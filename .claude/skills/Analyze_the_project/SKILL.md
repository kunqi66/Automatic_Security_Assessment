# 通读一个项目（Analyze_the_project）

## 这个 skill 要干成什么事

把一坨陌生的代码，变成**一个没碰过它的人半天能讲明白、并且能拿去面试**的文档。

判据只有一条 —— **读完的人能不能不看电脑，用自己的话把下面三件事讲出来**：

1. 用户点一下按钮，到屏幕上出结果，中间经过了哪些环节；
2. 这个项目里最容易出事、所以他们特意花了功夫防的地方是哪几处；
3. 面试官问「你在这个项目里负责什么、踩过什么坑」，他能答满三分钟且句句有细节。

**做不到第 3 条，这份文档就只是产品说明书，不是面试材料。**

---

## 铁律（先记住这几条，再动手）

### ① 人话优先，术语必须当场翻译

用户要的是**能看懂**，不是显得专业。

- 每出现一个术语，**第一次出现时立刻用一句大白话解释**，解释放在括号里或紧跟一句。
  - ✅ 「用到了 **RRF 融合**（把两路搜索的结果名次加起来重新排队，谁在两个榜上都靠前谁就排前面）」
  - ❌ 「采用了 RRF 融合策略进行多路召回结果的整合」
- 能不用术语就不用。「幂等」写成「**同样的操作做多少遍，结果都一样**」；
  第一次出现时再说「这个词叫幂等，面试会问」。
- **不要写**「先进的」「完善的」「高性能的」「企业级的」这类词。
  它们不提供任何信息，还占地方。

### ② 每条结论都要能指到证据

**写着写着就会开始编。** 防它的办法是：每个说法后面能跟出「文件:行号」或者一个**真实的数字**。

- ✅ 「权限检查在 [acl.py:41](../../../backend/engines/search_engine/acl.py) 拼成过滤表达式」
- ❌ 「系统在检索层做了权限过滤」

数字必须是**你亲自跑出来或数出来的**。数不出来就别写数字，写「没量过」。

### ③ 分清「代码里真有的」和「文档里声称的」

**项目文档会过期，而且过期时不会报错。** 同一个功能，文档写着「已实现」，代码里可能是空壳。

- 看到 README / 设计文档里的说法，**去代码里核一遍**再写进文档。
- 核不了（比如需要外部服务、跑不起来）就**明确标一句**「这条没验证，来源是文档」。
- 反过来，代码里有而文档没写的，往往是**最有价值的坑**，别漏。

### ④ 写「为什么」，不写「是什么」

「是什么」读者自己看代码就有；「为什么」只有做过的人知道。

- ❌ 「项目分了 api / engines / clients 三层」
- ✅ 「分这三层是为了让 api 层不许写业务、engines 层不许碰 web 框架 ——
  这样换掉 FastAPI 只动一层，而业务逻辑能脱离网络单独测」

**「为什么」是面试的分水岭。** 只会背「是什么」的人，简历上写什么都一样。

### ⑤ 坑和缺陷要写，而且要写够

面试官最想听的就是「你踩过什么坑」。所以：

- 每个不正常的设计背后**通常有一个真实的事故**，找出来讲。
- 项目**做得不好的地方也要写**，并写清「如果重做会怎么做」。
  这比吹「都做完了」可信得多 —— 面试官会追问，吹的地方一问就露。

### ⑥ 讲不到具体就说明没学会

每条知识点都要能回答：**「这东西在这个项目里具体长什么样？」**

答不上来，说明它只是从网上抄来的概念，不是这个项目的一部分 —— 那就别写进文档。

## 五步流程

### 第 0 步：先摸事实，不许凭印象

**目标**：知道这是个什么项目、能跑不能跑、有多少东西。

先看这些（**先看文件，别急着下结论**）：

| 看什么 | 想知道什么 |
|---|---|
| `README` / `CLAUDE.md` / `docs/` | 作者自己怎么描述这个项目 |
| 依赖清单（`pyproject.toml` / `package.json` / `pom.xml`） | 技术栈、几个模块、谁调谁 |
| 启动入口（`main.py` / `index.js` / `Application.java`） | 程序从哪里开始跑 |
| 目录树（只看两三层） | 代码按什么维度分的家 |
| 测试 / 验收脚本目录 | **最能看出这个项目在意什么** |
| 配置文件模板（`.env.example` 等） | 要连哪些外部服务，缺哪个就跑不起来 |

产出一张**事实表**，每条都带数字（多少张表、多少个接口、多少行、多少个模块）。
数字后面要用，别拍脑袋。

> ⚠️ **顺手记一下「这个项目故意不做什么」**。作者写「这里不做 X，因为 Y」的地方，
> 是理解设计意图最快的入口，也是面试时最能体现思考深度的素材。

### 第 1 步：拉出运行主线（这个 skill 的核心）

**目标**：从「用户的一个动作」追到「结果的最后一步」，一条一条画出来。

1. **先找主线，别贪多**。一个项目通常 3~6 条主线就够，例如：
   - 一次写操作：用户提交 → 校验 → 存库 → 回消息
   - 一次读操作：用户搜索 → 取数 → 加工 → 展示
   - 一条异步链路：收到的活儿 → 排队 → 后台慢慢干 → 干完回写
   - 一条定时链路：每隔多久 → 自动干点什么
   - 启动链路：程序起来那几秒做了什么

2. **每条主线写成「一步一行的表」**，每行三列：**谁 → 干了什么 → 在哪（文件:行）**。

3. **重点标出「岔路口」**。主线里凡是**可能出现第二种结果**的地方都要标：
   - 这里失败会怎样？是重试、是跳过、还是整个请求挂掉？
   - 这里有没有「不报错但结果不对」的可能？（**这是最危险的一类，要单独拎出来**）
   - 这里有没有并发/多进程的问题？

4. **追完整条链再回头写**。只看了前半段就下笔，一定会写错后半段。

> 🔴 **优先追「不报错但结果不对」的路径。** 崩掉的 bug 用户会报，
> 静默出错的 bug 能活几个月。这类地方往往就是项目里最值得讲的坑。

### 第 2 步：提炼「开发原理」

**目标**：把项目里**反复出现的做事规矩**抽出来。这些是「团队的思维方式」，
面试时讲这些，比讲功能更能说明你参与了设计而不是打杂。

找这几类：

- **分层规矩**：哪层不许干什么？（找作者写死的约束、注释里的「禁止」）
- **唯一入口**：哪些东西全项目**只能有一处定义**？（配置、密钥、状态存取…）
  为什么要这样？通常是因为「两处各写一份，改一处漏一处，且不报错」。
- **数据一致性**：什么情况下宁可一起失败也不许分开成功？
- **命名/编号规矩**：为什么这样命名？
- **一套流程**：这个项目要求新增一个功能时按什么顺序做？（先写文档？先写测试？）

每条都要写清：**规矩是什么 → 不守会出什么事 → 有没有自动检查兜着**。
**「有没有自动检查」这一条特别加分** —— 说明你知道「靠人自觉的规矩等于没有规矩」。

### 第 3 步：抽知识点（面试材料的主要来源）

**目标**：把项目里用到的技术点，逐个写成「能回答追问」的卡片。

抽的范围（按优先级）：

1. **这个项目的看家本领** —— 它区别于同类项目的那一两个设计；
2. **踩过坑的地方** —— 代码或注释里写着「曾经写成 X，后来改成 Y，因为 Z」的；
3. **通用但重要的技术** —— 缓存、队列、事务、并发、索引、流式传输……
4. **外部依赖的脾气** —— 每个第三方服务有什么反直觉的地方。

每张卡片**必须包含这七块**（少一块就不算完成）：

```markdown
### 知识点：<用大白话起标题，别用术语>

**一句话**：<不超过 30 字，外行也懂>

**为什么需要它**：<不用它会出什么事>

**这个项目里怎么做的**：<具体做法 + 文件:行>

**踩过的坑**：<真实的、能讲成故事的；没有就写「没踩过」>

**面试会怎么问**：<1~3 个真实的问法>

**你怎么答**：<照着念就能用的答案，**必须带这个项目的具体数字或例子**>

**追问会追到哪**：<面试官接着会问什么，怎么接>
```

> 🔴 **「你怎么答」里绝对不能只有概念。**
> 面试官问「你了解缓存吗」，他想听的是「我在项目里遇到过缓存改了不生效的问题，
> 因为索引放在进程内存里，发布之后别的进程不知道……」。**只有概念 = 背书，不算会。**

### 第 4 步：编一份面试题库

**目标**：面试前一小时能刷完的速查表。

分三类，每类 10~20 条：

| 类别 | 例子 |
|---|---|
| **项目本身** | 「介绍一下你这个项目」「最难的在哪」「为什么这样分层」 |
| **技术细节** | 「为什么用这个数据库」「这里并发安全吗」「失败了怎么办」 |
| **反问/深挖** | 「如果数据量涨 100 倍会怎样」「这块有什么不足」 |

每条只写**答案的骨架**（3~5 个词），详细内容指回第 3 步的卡片 —— 别重复。

⚠️ **必答的三道题**（谁的面试都躲不掉，文档里要有现成答案）：
1. **一句话说清这个项目是干什么的**（外行版，别堆术语）；
2. **你负责哪部分、最难的地方是什么**；
3. **这个项目有什么不足、你会怎么改**（**这题答不好最扣分**）。

### 第 5 步：自检

写完**逐条过一遍**，不合格就回去改：

1. **外行测试**：把开头那节给一个不懂这行的人看，他能说出这项目干啥的吗？
2. **证据测试**：随机抽 10 条结论，都能指到文件或数字吗？有一条指不出来就回去补。
3. **术语测试**：搜一遍文档里的专业词，每个都能在**第一次出现处**找到大白话解释吗？
4. **面试测试**：三道必答题，答案能说满三分钟吗？说不满就是细节不够。
5. **诚实测试**：文档里有没有写「不足」和「没验证」？
   **一条都没有，说明你在吹**，回去补。
6. **一致性测试**：文档里的数字，和你第 0 步量的对不对得上？对不上以代码为准。

## 输出什么

默认产出一个文件夹（路径按项目惯例，没有就放 `docs/` 或项目根的 `项目通读/`）：

```
项目通读/
├── README.md          # 索引 + 5 分钟速览（先读这个）
├── 01-这是什么.md      # 外行版介绍 + 能跑给谁看 + 技术栈人话表
├── 02-代码地图.md      # 目录结构 + 每块负责什么 + 从哪读起
├── 03-运行流程.md      # 第 1 步的主线，一步一行
├── 04-开发原理.md      # 第 2 步的规矩与理由
├── 05-知识点精讲.md    # 第 3 步的卡片，文档主体
└── 06-面试题库.md      # 第 4 步，按类别分
```

- **`README.md` 里的速览必须能在 5 分钟内读完**，读完知道这个项目干什么、
  最值得讲的三个点是什么。
- `05-知识点精讲.md` 是主体，可以很长，但**每张卡片要能被单独读懂**
  （别写成「见上文」）。
- 如果项目很小（万行以下），可以合成一个文件，但**章节编号保留**。

### 别忘了收尾

- 文档里凡引用代码，**用可点击的相对链接**，不要只写文字路径。
- 如果这个项目有「教学记录」「笔记」之类的既有文档，
  按项目惯例补一条指过去（**先看项目有没有这类约定，别自己发明**）。

## 反模式（写的时候躲开）

- ❌ **抄 README 和设计文档**。那些是「声称」，你要写的是「事实」。
- ❌ **只写目录结构就交差**。目录结构是地图，不是路线 —— 读者要的是**怎么走**。
- ❌ **知识点只写概念**。「什么是幂等」「什么是事务」满网都是，
  读者要的是「**这个项目里**它长什么样、踩过什么」。
- ❌ **报喜不报忧**。没有缺点的文档，面试时会当场露馅。
- ❌ **用「等等」「诸如此类」「类似地」偷懒**。这是漏写的地方，读者一眼能看出。
- ❌ **一份文档塞 50 个知识点**。宁可 15 个讲透，不要 50 个各讲一句 ——
  面试考的是能不能讲透，不是知道多少名词。
- ❌ **不看代码就写「实现了 X」**。这一行的代价是读者面试时说错话。

## 用这个 skill 时，怎么跟用户交代

写完之后，**在回复里说清这三件事**（别只说「写好了」）：

1. 文档在哪、建议按什么顺序读；
2. **哪些是核实过的、哪些是没验证的**（诚实交代）；
3. **这个项目最值得在面试里讲的 2~3 个点是什么** —— 这是用户最想要的一句话。
