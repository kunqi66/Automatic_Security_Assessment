# 如何让这套系统评估一个项目

> 写给：想自己复现一遍的人、以及面试时想验证「这套东西真能跑」的人。
> 本文里**每一条返回都是实测抓下来的**（2026-10-16，`ranges/ecommerce`，项目 #17 / 评估 #17），
> 不是从设计文档抄的。凡是没实测过的，我都标了「未实测」。

---

## 0. 最短路径：一条命令

```bash
cd backend
uv run python tools/e2e.py ecommerce      # 或 usercenter
```

`tools/e2e.py` 就是这个流程的脚本版：登录取 token → 建档 → 打包上传 → 启动评估 →
每 4 秒轮询五个阶段 → 打印漏洞清单与攻击链节点。它**只打 HTTP API，不 import `app`**，
所以它验证的是「真正部署起来的那条路径」，而不是某个内部函数能被调用。

本文余下的部分是**把这个脚本拆开讲**：每一步到底发了什么、返回什么、为什么这样设计。
要理解系统读这份，要跑通系统用上面那一条。

---

## 1. 两条路：界面（推荐）或 API

**评估一个新项目有两条路，结果完全一样** —— 界面上那个按钮就是本文第 3 节那三个
接口的封装，没有多做什么。

| 你想做的事 | 怎么做 |
|---|---|
| 评估一个**新**项目 | **界面上**：概览大盘（`/`）右上角「新建评估」，一个弹窗走完建档 → 补传 → 启动 |
| 同上，但不用界面 | 跑 `tools/e2e.py`，或按本文第 3 节手动打接口 |
| 看**已评估**过的项目 | 「概览大盘 → 最近任务」，点进去到工作台 |

### 界面这条路

按钮在概览大盘右上角，受 `assessment:create` 权限门控（需求 2.5.2）：

- **安全工程师**：可点。
- **管理员**：**看得到但是灰的**，悬浮会说明「当前角色（系统管理员）没有创建评估的
  权限，该操作需要安全工程师」。

管理员这里是禁用而**不是隐藏**，是有意的：藏掉按钮的话，管理员会以为这个系统根本
不能建评估，而实际他缺的只是一个角色 —— 灰按钮加一句为什么，比不存在的按钮有信息量。

这条路径由 `frontend/scripts/_e2e_new_assessment.mjs` 在真实浏览器里验过
（点开 → 填表 → 选文件 → 启动 → 跳工作台，16 项断言），跑法见该文件头部。

### 为什么下面还要留着 API 那条路

三个接口（`POST /projects`、`POST /projects/{id}/upload`、
`POST /projects/{id}/assessments`）是 SSOT，界面会变、接口不会。
排查「界面点了没反应」时，直接用 curl 打一遍就能定位是前端的问题还是后端的问题。

## 2. 前置：四个东西得同时活着

**缺任何一个的症状都不是「报错」，而是「卡住」或「静默不动」，所以先逐条确认。**

```bash
# ① SSH 隧道 —— 把 ECS 上的 MySQL / Redis 映射到本地 13306 / 16379
cd D:\myself_complete_code\agent\Automatic_Security_Assessment
ECS_PASSWORD=<口令> uv run --with paramiko python deploy/tunnel.py

# ② 后端 API（只管收发，不跑评估）
cd backend
uv run uvicorn app.main:app --host 127.0.0.1 --port 8010

# ③ 消费 worker —— **真正跑五个阶段的是它，不是 API**
cd backend
uv run python -m app.worker

# ④ 前端（只在你要看界面时才需要）
cd frontend
npm run dev
```

> **②③ 是两个进程，这是最容易踩的一脚。** API 只把任务 `xadd` 进 Redis 流就返回了，
> 评估是 worker 取走后才开始跑的。所以：
> **只起 API 不起 worker，接口会返回 201「启动成功」，然后评估永远停在 `created`。**
> 不报错、不失败、就是不动 —— 最坏的那种失败。

自检：

```bash
curl -s -o /dev/null -w "api=%{http_code}\n" http://127.0.0.1:8010/api/v1/health   # 期望 200
```

### 账号

```bash
cd backend
uv run python -m app.scripts.create_user --username engineer --role security_engineer
```

口令**只能从终端交互输入**（`getpass`），不接受 `--password` 参数 —— 参数会进 shell 历史
和 `ps aux` 的进程列表。自动化部署用 `--password-stdin`。

### 角色与权限（需求 2.5.2）

| 角色 | 写权限 | 只读 |
|---|---|---|
| `security_engineer` | `assessment:create`、`vuln:review`、`report:export` | 全部 |
| `developer` | `patch:accept` | 全部 |
| `admin` | `sandbox:manage`、`llm:manage`、`audit:view` | 全部 |

🔴 **管理员不能创建评估。** `assessment:create` 只给了安全工程师。
拿 admin 去 `POST /projects/{id}/assessments` 会 **403**，而那是**正确行为**。

权限是互补的、不是包含关系，所以别用「管理员权限最大」去推。前端也不自己推导 ——
`GET /auth/me` 直接返回 `permissions` 数组，判定一律走 `can(user, 'xxx')`：

```json
["assessment:view","audit:view","llm:manage","project:view","report:view","sandbox:manage","vuln:view"]
```

## 3. 六步走完

下面的 `$API` 是 `http://127.0.0.1:8010/api/v1`。命令是 **Bash** 写法。

### 第 1 步 · 换成 token

```bash
TOKEN=$(curl -s -X POST $API/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"engineer","password":"<你的口令>"}' | python -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
```

返回 `{access_token, token_type, user}`。**注意不是 `{code, message, data}` 信封** ——
本项目刻意不用信封（见 `schemas/common.py`），所以取值是 `body.access_token` 而不是
`body.data.access_token`。

### 第 2 步 · 建档

```bash
curl -s -X POST $API/projects -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"电商靶场","source_type":"upload"}'
```

```json
{"id":17, "name":"电商靶场", "source_type":"upload",
 "source_url":null, "source_branch":null,
 "storage_path":null, "description":null,
 "tech_stack":null, "total_loc":null,
 "status":"created", "error_message":null, ...}
```

⚠️ **`storage_path` 是 `null`** —— 这一步只写了一条占位记录，源码还没有。
`source_type` 只有两种：

- `"upload"` —— 走第 3 步，传 zip/tar。
- `"git"` —— 建档时会**同步浅克隆**（`--depth 1`，上限 300 秒），返回时 `storage_path` 已就位。
  需要在请求里带上 `"source_url"`，可选 `"source_branch"`（留空用默认分支）。

> **用 git 的话，地址必须在白名单内**，否则 400 `PROJ_GIT_NOT_ALLOWED`。
> 白名单来自 `GIT_URL_ALLOWLIST`（`backend/.env`），是**前缀匹配**。
> 它为空 = 不限制 —— 但那只允许在本地开发：生产环境为空会**直接启动失败**
> （`Settings._check_production_secrets`）。这个组合是刻意的：开发时懒得配，生产不配就起不来。
>
> 另外 `source_type=git` 是**同步克隆**，前端默认 30 秒超时会在 30 秒时断开，
> **而服务端的克隆还在继续、项目最后真的建出来了** —— 用户以为失败、实际成功，
> 很可能再点一次得到重复项目。所以客户端的超时必须放宽到 350 秒
> （`frontend/src/api/endpoints.ts` 的 `CREATE_PROJECT_TIMEOUT_MS`）。

### 第 3 步 · 补传源码包（`upload` 才需要）

```bash
curl -s -X POST $API/projects/17/upload -H "Authorization: Bearer $TOKEN" \
  -F "file=@ecommerce.zip"
```

```json
{"id":17, "storage_path":"17", "total_loc":648, "tech_stack":null, "status":"created", ...}
```

三个细节，都会让人误判：

1. **格式按 magic bytes 判，不看扩展名**（`_ZIP_MAGIC` / `_GZIP_MAGIC` / `_TAR_MAGIC`）。
   把 zip 改名成 `.tar.gz` 不会绕过，只会被拒。
2. **单一顶层目录会被剥离**（`_strip_single_root`）。所以 `ecommerce/app.py` 和
   `app.py` 两种打包方式**结果一样**，入库的 `file_path` 都是 `app.py`。
   不剥离的话漏洞表里会全是 `ecommerce/app.py`，前缀毫无意义却到处都是。
3. **`tech_stack` 到这里还是 `null`** —— 它是 recon 阶段回填的，不在上传这一步。
   上传只落盘 + 扫出 `total_loc`。

上限：单包总量 500 MB、条目数 50000（`archive_max_total_bytes` / `archive_max_entries`），
超了直接 400，不会解到一半才发现。

### 第 4 步 · 启动评估

```bash
curl -s -X POST $API/projects/17/assessments -H "Authorization: Bearer $TOKEN"
```

```json
{"id":17, "project_id":17, "project_name":"电商靶场", "status":"created",
 "current_stage":null, "progress":0, "security_grade":null,
 "stages":[{"stage":"recon","status":"pending",...}, ... 共 5 条], ...}
```

- **201**，不是 200。
- 五个阶段行**随评估一起建出来**，所以从第一秒起进度条就是完整的五步，
  而不是「先显示一步、跑起来才长出其余的」。
- 返回时 `status` 是 `created` —— worker 还没取走。**这不是失败。**
- 源码没到位时会 **400**：`该项目还没有源码，无法启动评估`。
- 项目已有在途评估时会 **400**：`该项目已有正在排队或运行中的评估`。
  「在途」= `created` **加** `running` —— 建行到被 worker 取走之间有个窗口，
  只判 `running` 会放它过去，连点两次就得到两条评估、白跑一整轮（实测过：
  第一次 POST 之后紧接着第二次，修之前返回的是 **201**）。

### 第 5 步 · 盯进度

两种方式，选一个：

```bash
# ① 轮询（e2e.py 用的就是这个）
curl -s $API/assessments/17 -H "Authorization: Bearer $TOKEN"

# ② SSE 实时日志流（前端工作台用的）
curl -N $API/assessments/17/stream -H "Authorization: Bearer $TOKEN"
```

SSE 是 **Redis Stream 不是 Pub/Sub**，所以断线期间的日志不会丢：浏览器重连时把上次收到的
消息 id 作为 `Last-Event-ID` 头回传，从那个 id 之后补读。首连（不带头）从 `0-0` 开始，
也就是**把保留的历史全推一遍** —— 点开一个跑了十分钟的评估，应该立刻看到那十分钟，
而不是从空白开始。

### 第 6 步 · 拿结果

```bash
# 漏洞清单
curl -s "$API/assessments/17/vulnerabilities?page_size=100" -H "Authorization: Bearer $TOKEN"

# 攻击链节点（注意：是节点，不是链）
curl -s $API/assessments/17/chains -H "Authorization: Bearer $TOKEN"

# 报告
curl -s "$API/assessments/17/report?format=md" -H "Authorization: Bearer $TOKEN"
curl -s -o report.md "$API/assessments/17/report/download/md" -H "Authorization: Bearer $TOKEN"
```

`GET /report` 返回的是**元数据**（`status` / `size_bytes` / `content_path`），
正文在 `/report/download/{fmt}`。这让很多人以为报告是空的 —— 实测 `?format=md`
只返回 227 字节，而正文实际有 68041 字节。

## 4. 一次完整的实测记录

`ranges/ecommerce`（5 个文件 = `app.py` 323 行 + `admin_login.py` 53 + `config.py` 67 +
`db.py` 78 + `GROUND_TRUTH.yaml` 250，共 11 条钉死的 GROUND_TRUTH），2026-10-16 走了一遍：

```
0. POST /auth/login                 -> 200   (JWT 长度 207)
1. POST /projects                   -> 201   id=17  storage_path=null  status=created
2. POST /projects/17/upload         -> 200   storage_path="17"  total_loc=648  tech_stack=null
3. POST /projects/17/assessments    -> 201   assessment_id=17  status=created  stages=5
3b. 紧接着再 POST 一次               -> 400   "该项目已有正在排队或运行中的评估"
4. 轮询 ...                          -> completed  用时 191s
     轨迹: running/-/0  ->  running/code_audit/40  ->  running/poc_verify/40
           ->  running/exploit_chain/60  ->  running/report_gen/80  ->  completed/-/100
     security_grade = "critical"（报告里写作「极高危」，安全评分 3.82 / 100）
     五个阶段全部 completed，note 皆为 null（无降级、无跳过）
5. GET /vulnerabilities             -> 200   total=15   状态分布 {verified: 8, potential: 7}
6. GET /report?format=md            -> 200   status=ready  size_bytes=68041  content_path=17/report.md
     download/md   -> 200   68041 字节
     download/html -> 200  124633 字节
     download/pdf  -> 404
```

耗时分布（报告里的流水线摘要）：`recon` 1 秒、`code_audit` 2 秒、
**`poc_verify` 146 秒**、`exploit_chain` 11 秒。

**评估的总耗时基本由「漏洞条数」决定，而不是由代码量决定。** worker 日志里
`开始验证漏洞 N` 每隔 **9 秒**出现一行，15 条正好约 140 秒：

```
19:59:59  开始验证漏洞 136（hardcoded_secret）：计划 4 条探针
20:00:09  开始验证漏洞 137（sql_injection）  ：计划 2 条探针
20:00:18  开始验证漏洞 138（sql_injection）  ：计划 2 条探针
20:00:27  开始验证漏洞 139（sql_injection）  ：计划 2 条探针
...
```

这个 9 秒**与探针条数无关**（漏洞 136 计划 4 条、漏洞 141 计划 1 条，实测都是 9 秒），
因为开销按**每条漏洞一组沙箱容器**算，不是按每条探针：`runner._group_budget`
给整组算的是「部署 + Σ(每条请求超时) + 15 秒余量」。所以「评估慢」几乎总是
`poc_verify` 慢，而它是五个阶段里唯一会启动容器的那个。

```

#140  critical verified   sql_injection      app.py:114-116     cvss=10  sink=cursor.execute

#143  critical verified   command_injection  app.py:194-196     cvss=10  sink=subprocess.check_output

#142  critical verified   path_traversal     app.py:165         cvss=9.3 sink=send_file
#144  critical verified   path_traversal     app.py:220         cvss=9.3 sink=open
#145  critical verified   path_traversal     app.py:241         cvss=9.3 sink=send_file
#137  critical potential  sql_injection      admin_login.py:43-49 cvss=9.1 sink=cursor.execute
#138  critical potential  sql_injection      admin_login.py:43-49 cvss=9.1 sink=cursor.execute
#136  medium   potential  hardcoded_secret   admin_login.py:23  cvss=5.5 sink=ADMIN_PASSWORD
#147  medium   potential  hardcoded_secret   config.py:26       cvss=5.5 sink=SECRET_KEY
#148  medium   potential  hardcoded_secret   config.py:27       cvss=5.5 sink=DB_PASSWORD
#149  medium   potential  hardcoded_secret   config.py:28       cvss=5.5 sink=API_KEY
#150  medium   potential  hardcoded_secret   config.py:32       cvss=5.5 sink=ADMIN_TOKEN
```

> **`admin_login.py:43-49` 那两条看着像重复，其实不是。** 它们是**同一个下沉点上的两条
> 独立污点路径**，源头不同，两条都可达：
>
> ```
> #137  source:request.form.get@app.py:304 -> propagate:username@admin_login.py:29 -> sink:cursor.execute@admin_login.py:43
> #138  source:request.form.get@app.py:305 -> propagate:password@admin_login.py:29 -> sink:cursor.execute@admin_login.py:43
> ```
>
> app.py:304 是 `username`，305 是 `password` —— SQL 拼接里两个变量都没转义，
> 所以是两个可独立利用的注入点。**但报告里这两行读起来一模一样**（同类型、同文件行、
> 同严重度），看的人很容易当成去重没做好。要区分得点开看 `taint_trace`。

## 5. 结果怎么读 —— 哪些是实测，哪些是推演

这套系统的第一原则是**「拿掉 LLM，结论一字不变，只有措辞会变」**。
所以真正要区分的是下面这两组，而**都不是**「LLM 说的」：

### `verified` vs `potential`

| 状态 | 含义 |
|---|---|
| `verified` | 沙箱里**真的跑过**探针，且探针命中了。这是实测。 |
| `potential` | 静态分析判定可达，但**没有在沙箱里验证成功**。可能是探针没写、环境不满足、被 `HarmlessGuard` 拦了。 |
| `unverified` | 还没有跑过验证 |
| `rejected` | 人工复核判定为不成立（`PATCH /vulnerabilities/{id}`） |

上例中 8 条 `verified` 全是 `critical`，7 条 `potential` 里有 2 条 `critical`。
**`potential` 不是「低置信度」的同义词，它是「没验证」** —— 报告里的评分与等级会
把 `verified` 的高危算得更重（`report/scoring.py` 的 `has_verified_high`）。

### 攻击链上的 `verified` vs `inferred`

攻击链节点有独立的 `verification_status`：

- `verified` —— 这一环实际执行过
- `inferred` —— **引擎按 R1–R8 规则推演出来的，没有实际执行**

报告里必须声明哪些环是推演的。这是硬要求：把推演说成实测就是造假。
`tools/e2e.py` 打印节点时会带上 `推演=` 字段，就是给这个用的。

⚠️ `GET /assessments/{id}/chains` 返回的是**节点**，不是链。
本次实测：**4 条链、共 15 个节点**（`chain_id` 有 35/33/34/36 四个值），
其中 `verified` 10 个、`inferred` 5 个，命中规则 R1 / R2 / R3 / R6 / R8。

`e2e.py` 早先在这上面栽过：它把这个数组的长度写成「利用链 N 条」，在另一个靶场上
印出 28 —— 而链数要低一个数量级。**把节点数当链数是个只会往大了错的标签**，
会让人以为串出了 28 条攻击路径。链数要查表。

### 两次运行之间，什么变了、什么没变（实测）

上面那句「拿掉 LLM，结论一字不变」不应该只是宣称，所以拿同一靶场跑了两遍做对照：
**#17 走 API（`tools/e2e.py` 那条路），#20 走界面（点「新建评估」那条路）**，
然后逐字段比。

| 比什么 | 结果 |
|---|---|
| 漏洞签名（类型 + `file_path` + `line_start` + `status` + `severity` + **`confidence`**） | 15 条，**逐条相同** |
| 报告里出现的全部 `文件:行` 坐标 | 40 种，**集合完全相同** |
| 攻击链节点（带父子关系的结构签名：父类型 + 类型 + 验证状态 + 规则 + 文案） | 15 个，**逐条相同** |
| 用到规则 / 验证状态分布 | `R1,R2,R3,R6,R8` / `10 verified + 5 inferred`，**相同** |
| 安全等级、五个阶段终态 | `critical` / 五阶段全 `completed`，**相同** |
| 报告正文措辞 | **不同**（LLM 生成，本就该不同） |
| 各阶段耗时（如 `poc_verify` 146s vs 142s） | **不同**（本质随机） |
| PoC 里的金丝雀串（`asa92c6f219acee` vs `asa6fcdc64034c6`） | **不同**（每次新生成本来就更可信） |

两份 markdown 报告 68041 vs 68489 字节，`diff` 出 316 行 —— **全部落在上表后三行**。
换句话说：**变动只发生在表达层，判定层一个字都没动。**

⚠️ 比的时候踩过一个坑，值得记下来：`GET /assessments/{id}/chains` 返回的是
**扁平数组**，不是 `{nodes: [...]}`。第一版对照脚本写了 `resp.nodes ?? []`，
两边都拿到空数组，于是「差异 = 0」—— **一个什么都没比的绿色通过**。
链节点那一行现在比的是 `id`/`chain_id`/`vuln_id` 归一化之后的结构签名，
不是数组长度。凡是「两边都空所以相等」的断言，都要先确认它拿到过东西。

## 6. 失败速查

| 症状 | 真实原因 | 怎么办 |
|---|---|---|
| `401` | 没带 token / token 过期 | 重新登录 |
| `403` 建档或启动评估 | **用了 admin** | 换 `security_engineer` 账号 |
| `400` `该项目还没有源码` | 建档后没传源码 | 走第 3 步上传 |
| `400` `该项目已有正在排队或运行中的评估` | 有在途评估（含 `created`） | 等它结束，或 `POST /assessments/{id}/stop` |
| `400` `PROJ_GIT_NOT_ALLOWED` | Git 地址不在白名单 | 改用源码包，或配 `GIT_URL_ALLOWLIST` |
| 启动返回 201，但**永远停在 `created`** | **worker 没起** | 起 `uv run python -m app.worker` |
| 启动返回 503 | Redis 不可用 | Redis 是存储类依赖、**不可降级**：队列不通就没有「稍后重试」 |
| 克隆卡住不动 | 需要认证的私有仓库在等口令 | `GIT_TERMINAL_PROMPT=0` 已设；确认仓库是公开的 |
| 上传大包在 30 秒断开 | 客户端默认超时太短，**服务端还在继续** | 别重试，先查项目是不是已经建好了 |
| 报告正文「打不开」 | 拿的是 `/report` 元数据 | 正文在 `/report/download/{fmt}` |
| 前端页面全白 | 大概率是后端没起 / token 失效 | 看浏览器控制台，不一定是前端的问题 |

## 7. 已知限制（都是实测出来的，不是猜的）

这几条不影响主流程，但面试时被问到不该答不上来。

1. **PDF 导出没有实现。** `download/pdf` 返回 **404**，报 `该评估还没有 pdf 格式的报告文件`。
   措辞是「还没有」，听起来像稍后会有 —— 实际是没写这个渲染器。
   实测可用的只有 `md`（68041 字节）和 `html`（124633 字节）。

2. **报告里「评估结束」永远显示「未结束」，「总耗时」永远是「—」。**
   `report.md.j2` 用 `d.meta.finished_at` 判断，但报告是在 `report_gen` 阶段生成的，
   那时整个评估还没结束、`finished_at` 尚未写入。所以**每一份报告**都带着这两处空值。

3. **报告第一段的「降级说明」排版是粘连的**，实际渲染成：

   ```
   > **本次报告的降级说明：** `llm`> 降级只影响呈现方式，不影响漏洞清单、评分与排序等任何结论。
   ```

   `` `llm` `` 和后面的 `>` 挤在同一行，那个 `>` 因此不会被当成引用块。
   根因是 Jinja 的 `{% endfor %}` 吃掉了行尾换行（`report.md.j2:19`）。

4. **`Project.status` 在成功路径上永远停在 `created`。**
   `projects/service.py` 只在失败时写 `FAILED`，`running` / `completed` / `stopped`
   这三个枚举值**没有任何代码写入**。所以别拿项目 `status` 判断「评估完了没有」——
   要判断得看 assessment。这也是为什么建完档的项目看起来「没动过」。

5. **同一 `file:line` 出现多条不一定是重复**（见 §4 的 `admin_login.py:43-49`）。
   报告里不会解释这一点，得点开 `taint_trace` 才看得出是两个源。
