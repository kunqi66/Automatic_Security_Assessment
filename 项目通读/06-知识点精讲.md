# 卡片 1 · 可控多智能体（L1–L4）

### ① 一句话
**把大模型关在表达层：结论全由确定性代码算，LLM 只负责把结论说成人话。**

### ② 为什么需要它
用 LLM 做安全分析，最大的问题是**不可复现**：同一份代码扫两遍，
今天说有注入、明天说没有。用户没法信。

### ③ 这个项目里怎么做的
四条铁律（`概要设计总纲.md:619-632`），每条都有**代码里的落点**：

| 铁律 | 含义 | 落点 |
|---|---|---|
| **L1 不参与判定** | 漏洞有无/类型/严重度/CVSS/状态/攻击链节点与边/评分/整改顺序**全由代码产出** | `llm/types.py:226-259` 的返回类型**根本没有这些字段** |
| **L2 不引入事实** | 结构化字段一律代码填充，LLM 只填自由文本 | `prompts.py:12-14` 把已判定事实作为 known facts 喂进去 |
| **L3 输出必校验** | 描述走实体白名单，叙事走节点集合比对，补丁走四道校验 | `llm/guard.py:114` `check_entities()` |
| **L4 可降级不阻断** | 无 key/超时/限流/畸形/校验不过 → 一律降级，不抛给调用方 | `llm/fallback.py`（437 行） |

**封闭用点只有四个，多一个都不许加**（`llm/__init__.py:7-14`）：

| 用点 | 写进哪个字段 | 类型 |
|---|---|---|
| ① `describe_finding` 漏洞描述 | `vulnerabilities.description` | 文本 |
| ② `suggest_patch` 补丁 Diff | `patches.diff_content` | 文本 |
| ③ `narrate_chain` 攻击链叙事 | `ChainEntry.narrative` | 文本 |
| ④ `suggest_remediation` 整改建议 | `Recommendation.note` | 文本 |

**四个都是纯文本列，没有一个是判定字段。**

### ④ 代码长什么样

状态字段的**唯一写入方**（`agents/poc_verify.py:203-205`）：

```python
    # `status` 由 B5 判定，这里只搬运 —— 那正是 L1 要挡的东西
    row.status = result.status
```

静态阶段写死（`agents/code_audit.py:181`）：

```python
        status=VulnStatus.UNVERIFIED,     # 静态阶段恒为 unverified
```

类型层的硬堵（`llm/types.py:226-232` 的 docstring）：

```python
    """……**只有文本与来源标注，没有任何参与判定的字段**。"""
```

### ⑤ 为什么不那样做
**不用"让 LLM 判断严重度、代码复核"这种混合模式。**
因为一旦模型能影响判定，判定的**可复现性**就依赖模型版本、温度、网络。
而且"复核"本身也要写规则 —— 那不如直接让规则判定。

### ⑥ 踩过的坑
- `llm/expressions.py:24-26` 的注释点明了要害：
  **「想让 LLM 的产出影响阶段跳转或排序，得先改这个模块的类型定义」** ——
  把"不该做"变成"做起来很别扭"，比写注释警告有效。
- 降级日志的**级别是 INFO 不是 WARNING**（`expressions.py:73-76`）——
  因为降级是**设计内的正常路径**，不是异常。

### ⑦ 面试会怎么问
> 「你说 LLM 不参与判定 —— **怎么证明？**」

### ⑧ 你怎么答（必须带数字）
三句话：

1. **类型层**：四个用点的返回类型 `TextResult` / `PatchDraft`
   只有 `text`/`diff`/`llm_model`/`degraded`/`reason` 五个字段，
   **没有 severity / status / 排序**。想让模型影响判定，得先改类型定义。
2. **写入层**：`vulnerabilities.status` 全项目只有两个写入方
   （`code_audit.py:181` 写死 `unverified`、`poc_verify.py:205` 从探针结果搬运），
   **都在确定性代码里**。
3. **判据层**：**「拿掉 LLM，系统的结论必须一字不变，只有措辞会变」** ——
   这句话有测试：`test_llm_fallback.py`（四个用点全部降级后仍产出可交付文案）、
   `test_report_assembler.py:287`、`test_chain_narrative.py:8`、
   `test_report_render.py:506`。

**加一个数字**：`llm/` 一共 2,062 行，其中 `fallback.py` 就占了 **437 行** ——
**降级模板比调用逻辑还多**。这本身就说明"可降级"不是事后补的。

### 追问三层
- **追问 1**：「那 LLM 在这系统里到底有什么用？」
  → 只改善**可读性**。四个用点产出的都是给人看的文本。
  拿掉之后报告依然完整、结论依然正确，只是描述变成模板腔。
- **追问 2**：「模板降级了，用户看得出来吗？」
  → 看得出来，而且**必须看得出来**：报告里有 `degraded` 列表逐项登记，
  补丁有 `source` 三态（`llm`/`template`/`validate_failed`）前端**绿/蓝/红**区分
  （`PatchSection.tsx:9-13`，注释写「**绝不能长成一个样子**」）。
- **追问 3**：「如果让你加第五个用点呢？」
  → 先问**它的产出会不会进控制流**。如果会，那就不加 ——
  这是 `llm/__init__.py:14`「**多一个都不许加**」的意思。
  如果只是文本，加之前必须：① 进 `fallback.py` 写确定性模板
  ② 进 `guard.py` 定白名单 ③ 补"拿掉 LLM 结论不变"的测试。

# 卡片 2 · 静态污点分析（tree-sitter）

### ① 一句话
**自己写的 SAST：从"脏数据从哪进来"出发，沿着赋值和拼接一路走，走到危险函数就报。**

### ② 为什么需要它
不这么做就退化成**关键字匹配**：看见 `execute()` 就报。
那样误报会多到不可用 —— 而安全工具的误报是致命的（用户会整体不信）。

### ③ 这个项目里怎么做的
`backend/app/analysis/`（5,574 行，全项目最厚）。五个零件：

| 文件 | 内容 | 条数 |
|---|---|---|
| `sources.py` | 脏数据从哪来（`request.args` 等） | **41 条** |
| `sinks.py` | 危险函数（`execute`、`eval` 等） | **35 条** |
| `sanitizers.py` | 净化函数（`escape`、`quote` 等） | **16 条** |
| `propagators.py` | 数据继续流的规则（赋值、拼接） | **34 条** |
| `taint.py` | **传播算法本体** | — |

**用 tree-sitter 而不是 Python 内置 `ast`** —— 因为内置 ast
遇到语法错**直接抛异常**，而真实工程里的 `.py` 常带语法错（Python 2 代码、
半截文件）。tree-sitter 是容错的，能给出部分树。

**只注册了 python 一种 grammar**（`parser.py:31-33`），其他语言**显式报错**
而不是静默跳过。

### ④ 代码长什么样

**结构性保证：必须一个"脏"的实参真的到达危险函数**（`taint.py:657-663`）：

```python
    dangerous = _dangerous_args(spec, node, positional, keywords, ctx)
    for arg_node, value in dangerous:
        if value is None or not value.dirty:      # ← 实参不是脏的 → 不报
            continue
        if spec.vuln_type in value.sanitized_types:   # ← 已被净化 → 不报
            continue
```

**跨函数只展开一层**（`taint.py:766-781`）：

```python
def _handle_project_call(node, dotted, receiver, positional, keywords, env, ctx):
    """项目内调用：跨函数展开（一层）或标记未展开。"""
    candidates = ctx.table.candidates(dotted, ...)
    if ctx.function.qualname in candidates:
        # 递归/自调用：**不做展开**。静态展开递归需要不动点，而递归函数的
        # 污点结论本来就依赖调用深度 —— 假装能算出来才是错的。按未展开标注。
        ctx.calls_self = True
```

### ⑤ 为什么不那样做
- **不做到任意深度的跨函数分析**：需要不动点迭代，复杂度和误报都会上去。
  现在只展开一层，**剩下的显式标 `unexpanded`**。
- **不追递归**：理由写在代码里了 ——「假装能算出来才是错的」。

### ⑥ 踩过的坑
**最大的一个：`_has_shell_true` 恒为 False**（详见 [04-代码精读.md](04-代码精读.md) 精读 2）。
tree-sitter 给布尔字面量的节点类型是 `"true"` 不是 `"boolean"`，
于是 `subprocess.run/call/check_call/check_output/Popen` **五个符号的
`shell=True` 命令注入一条也报不出来**。

**为什么测试没抓到**：正例用的是 `os.system`（不走这个判断），
反例用的是 `subprocess.run(shell=False)` —— 它"通过"的真实原因不是
"正确识别了 shell 参数"，而是"**压根没识别 shell 这个参数**"。

### ⑦ 面试会怎么问
> 「你这个静态分析器，**怎么控制误报**？」

### ⑧ 你怎么答（带数字）
**三层控制，从结构到策略**：

1. **结构性保证**：`taint.py:657-663` —— 必须一个脏实参**真的到达** sink 才产出。
   光看见危险函数不算。
2. **三类豁免**（`taint.py:722-727`）：参数化 SQL 的绑定值、
   `shell=False`、`yaml.safe_load` —— 每一条都对应一类"正确写法被误报"。
3. **策略层**：**「报多」与「漏」代价不对称**（`analysis/__init__.py:36-52`），
   默认偏向报多，但把 **10 条已知精度边界逐条登记**、每行标"漏"还是"报多"。

**数字**：规则共 **41 source + 35 sink + 16 sanitizer + 34 propagator = 126 条**；
靶场实测 **14/16 召回（87.5%）、误报 0**。

### 追问三层
- **追问 1**：「为什么不用现成的 SAST（Semgrep / CodeQL）？」
  → 诚实答：**这个项目要证明的正是"引擎是我自己写的"**。
  而现成工具拿不到逐行的污点路径（CodeQL 可以但查询语言另学一套），
  而本项目要把**每一跳的 file:line** 存进 `taint_paths` 表给前端画出来。
  另外沙箱断网，装不了。
- **追问 2**：「跨函数只展开一层，会漏多少？」
  → 诚实答：**不知道具体数字，没量过**。但影响是明确的：
  调用链超过两跳的漏洞会漏，且会标成 `unexpanded` 而不是静默丢弃。
- **追问 3**：「精度边界那 10 条举三个。」
  → ① 只支持 Python；② 跨函数只一层；③ 不做别名分析
  （`a = b; a = c` 之后 `b` 的污点状态）；
  其余在 `analysis/__init__.py:36-52` 的表里。

# 卡片 3 · 四态判定（verified / potential / rejected / unverified）

### ① 一句话
**把"我确认了"和"我怀疑但没证明"分开说 —— 这是整份报告可信度的地基。**

### ② 为什么需要它
安全工具最常见的伤害不是漏报，是**过度归因**：
把"这类问题在本目标上存在"说成"**你这一行有问题**"。
用户照着去改，改完发现没解决 —— 信任就没了。

反过来，把"没验证出来"说成"没问题"更糟（见卡片 11）。

### ③ 这个项目里怎么做的
`需求.md:37-39` 定的规则，代码里落在 `vulnerabilities.status`：

| 状态 | 含义 | 怎么产生 |
|---|---|---|
| `unverified` | 静态扫到，还没验 | `code_audit.py:181`（写死） |
| `verified` | **逐点确认**：这一行被探针跑通了 | `poc_verify.py:205` |
| `potential` | **仅类别级**：这类问题在目标上存在，但没证明是这一行 | 同上 |
| `rejected` | 被动态证伪 | 同上 |

**`rejected` 在整个系统里只有一个入口**：`can_conclude_absence`
（`verify/` 里，有专门的测试文件 `test_verify_absence.py`）。

### ④ 代码长什么样

`rejected` 的中文措辞被改过（`report/types.py:66-77`）：

```python
    # 原先是「已复核排除」，而**没有任何人工复核发生在这一步**……
    # 报告的措辞若说「人工已排除」，读者就不会去复核它 ——
    # 这正是假阴性得以存活的方式。
    "rejected": "动态未复现（机器判定，待人工确认）",
```

### ⑤ 为什么不那样做
**不把 `potential` 合并进 `verified`。**
合并能让报告"好看"（确认率高），但那是拿可信度换数字。

**也不把 `potential` 当噪音删掉** —— 缩略语（`需求.md:39`）：
「未通过 PoC 验证但存在风险模式的代码，标为中低危潜在隐患，**防止误报干扰**」。

### ⑥ 踩过的坑
**两条真 SQL 注入被判成 `rejected`**（`test_verify_absence.py` docstring）：

> 因参数名推导错被打成 `rejected`……「**三个环节每步都对，结论是错的**」。

以及 `SELECT *` 列数返回 1 那个级联失效（[04-代码精读.md](04-代码精读.md) 精读 3）。

**`rejected` 的 bug 之所以危险**：它让真漏洞**从报告里消失**，
而不是多出一条噪音。

### ⑦ 面试会怎么问
> 「`verified` 和 `potential` 有什么区别？**为什么要分？**」

### ⑧ 你怎么答（带数字）
- **`verified` = 逐点确认**：探针在容器里跑通，响应回显了随机 nonce，
  有请求/响应原始报文当证据。
- **`potential` = 仅类别级**：没拿到回显，但风险模式还在。
  **它不声称"是你这一行"**，只声称"这类问题在本目标上存在"。
- **分的原因**：报告是给人**照着改代码**的。归因错了，改的地方就不对。
  靶场上一次评估的典型分布是**11 条疑似 → 5 verified / 3 potential / 3 rejected**
  （具体数字随靶场变，见你的实跑输出）。

**加分的一句**：`rejected` 的措辞从「已复核排除」改成了
「**动态未复现（机器判定，待人工确认）**」—— 因为前者会让读者**跳过复核**。

### 追问三层
- **追问 1**：「`potential` 的严重度怎么定？」
  → 按 `需求.md:39` 定为**中低危**。理由：动态没验出来，
  说明利用条件可能不成立，但不能因此说没问题。
- **追问 2**：「怎么防止 `rejected` 误判？」
  → ① `can_conclude_absence` 是唯一入口，有专门测试；
  ② 模块原则是「**宁可漏报，不可误拒**」（`verify/context.py` 文件头）；
  ③ `potential` 这个中间态本身就是缓冲 —— 拿不准时不必二选一。
- **追问 3**：「如果探针跑不起来（沙箱挂了）呢？」
  → 整个 `poc_verify` 阶段标 `skipped`，**所有漏洞保持 `unverified`**，
  **不会**变成 `rejected`。因为"没验"和"验了没问题"是两件事（卡片 9）。

# 卡片 4 · 动态无害化验证（探针 + nonce）

### ① 一句话
**在断网容器里把靶场跑起来，发一条无害请求，看响应有没有回显出埋进去的随机串。**

### ② 为什么需要它
静态分析的误报率天然高（上下文不足）。**真的跑一次**是最强的证据。

### ③ 这个项目里怎么做的
```
sandbox/    起容器（Docker over SSH），network_disabled=True，只读挂载源码
verify/probe.py    漏洞类型 → 探针模板，载荷里埋一个随机 nonce
verify/runner.py   发请求，看响应里有没有 nonce
```

**关键：载荷是"无害"的。** SQL 注入的探针只做 `UNION SELECT <字面量>`，
**不读数据、不写数据、不删数据**。看到 nonce 回显就证明注入成立。

### ④ 代码长什么样

载荷里的第二列**曾经是 `version()`**（`verify/probe.py:195-199`）：

```python
    # 第二列**原本是 `version()`**，改成字面量是实测逼出来的：
    # `version()` 是 MySQL/PG 专有函数，SQLite 上直接 `no such function: version`，
    # 而 PRD §10.1 规定的靶场正是 SQLite ——
    # **交付的载荷打不穿自己文档规定的靶场**。
```

### ⑤ 为什么不那样做
**不用 `sleep(5)` 之类的盲注探针** —— 虽然也是一种"无害"，
但它慢、且依赖时间测量（在容器里不稳定）。
**nonce 回显是确定性的**：有就是有，没有就是没有。

**更不真的拖库/RCE** —— 见卡片 5 的无害化红线。

### ⑥ 踩过的坑
**① 探针路由是写死的**（`verify/probe.py:183` 起）：
`/search`、`/api/ping`、`/api/file`、`/api/download`、`/api/upload`、
`/api/user/profile`、`/api/user/list`、`/.env`、`/debug/config`、`/api/deserialize`。

**后果**：面对一个真实工程，探针**很可能一个端点都打不中** →
所有漏洞只能停在 `potential`。

**② 入口和工作目录也写死**（`probe.py:1240-1241`）：
`app_entry = "app.py"`、`workdir = "/workspace"`。
`ranges/README.md:74-76` 印证：「**改名或挪位置不会报错，只会超时**」。

**③ "命中但非本条端点"**（`runner.py:374`）：
探针在 A 端点拿到回显，于是判定 B 端点（同类型漏洞）也成立。
**靶场上这是个可接受的近似，真实工程上就是误报来源。**

### ⑦ 面试会怎么问
> 「你怎么保证探针是**无害**的？」

### ⑧ 你怎么答（带数字）
**三层防止**：

1. **环境层**：容器 `network_disabled=True` —— **断网，无出口**。
   所以即使被测代码里有反弹 Shell，也连不出去。
2. **载荷层**：SQL 注入用 `UNION SELECT <字面量>`，命令注入用
   `echo <nonce>`（不是 `whoami`、不是读 `/etc/passwd`）。
   **改的是"能不能看见 nonce"，不是"能拿到什么数据"。**
3. **设计层**：攻击链最后一环（WebShell → RCE）**只推演不执行**（卡片 5）。

**代价要说清**：容器断网意味着**不能 `pip install`**，
所有依赖必须预打进镜像。这也是沙箱镜像至今"未构建"时
`poc_verify` 会**静默降级为 skipped** 的原因。

### 追问三层
- **追问 1**：「探针打不中端点怎么办？」
  → 该漏洞停在 `potential`，**并如实标注"未获动态确认"**。
  不会当成 `rejected`，也不会硬说 `verified`。
- **追问 2**：「写死的路由怎么改？」
  → 应该从 `recon` 阶段的实际路由清单里生成探针目标，
  而不是查模板表。这是**已知改进方向**，现在没做。
- **追问 3**：「nonce 会不会被被测应用'意外'回显，造成假验证？」
  → 会。nonce 是随机串，但如果是回显型接口（把输入原样返回），
  任何输入都会被回显。所以模板里对有回显风险的端点
  要用**结构化的判据**（比如 `UNION` 的结果列数），不能只看"响应里有 nonce"。

# 卡片 5 · 攻击链推演与无害化红线

### ① 一句话
**把已确认的漏洞串成 DAG，最后一环靠推演 —— 并且明确标出它是推演。**

### ② 为什么需要它
单个漏洞的危害有限，"注入 → 拿凭证 → 上传 WebShell → RCE"这种组合
才是真实攻击路径。用户需要知道**先堵哪一环能打断整条链**。

### ③ 这个项目里怎么做的
`backend/app/chain/`（1,525 行）规则引擎，按"资产权限跃迁逻辑"组装
（`需求.md:41`）。落库见卡片 6 的 `attack_chain_nodes` 表。

**关键设计：`verified` / `inferred` 两态**——
链上每一环标明是**实测**的还是**推演**的。

### ④ 代码长什么样

**不建边表**（`models/chain.py:3-4`）：

```python
    """关键设计：不建边表。

    DAG 的边完全由 `parent_node_id` 自引用派生 —— 节点数远少于边数，
    一张自引用表就够，且**天然不会出现「边指向不存在的节点」**。
    """
```

### ⑤ 为什么不那样做
**不真的执行 RCE。** 设计文档 `概要设计总纲.md:760` 明确否决了
"真的执行 RCE 来验证"这个方案。理由：违背无害化原则。

**不建边表**：节点数远少于边数，一张自引用表就够，
而且从结构上消除了"悬挂边"这类脏数据。

### ⑥ 踩过的坑
**"最后一环"在报告里的措辞必须极小心。** 正确的说法是：

> 第 1–2 环已无害验证，第 3 环由**已证实的前置条件推演得出，未实际执行**。

少了后半句，读者会以为系统真的打穿了 —— 那是在**虚报战果**。

### ⑦ 面试会怎么问
> 「你的攻击链，最后一步 RCE 是**真的打出来**的吗？」

### ⑧ 你怎么答（带数字）
**不，是推演。而且这是刻意的。**

- 前几环（SQL 注入、文件上传）**已无害验证**，有探针证据；
- 最后一环（上传 WebShell → 宿主机执行）**由已证实的前置条件推演**，
  数据结构里标成 `inferred`（不是 `verified`）；
- 报告里写明"未实际执行"。

**为什么不打**：① **无害化原则** —— 扫描器可以推断"这里能打穿"，
但绝不应该自己打穿；② 上传 WebShell 会**真的修改被测系统**，
那不是"验证"是"入侵"；③ 万一被测的是生产环境的镜像，后果不可控。

**加分**：设计文档 `概要设计总纲.md:760` 里把这个方案**明确否决过**，
不是我没想到。

### 追问三层
- **追问 1**：「那这条链的可信度有多高？」
  → 标了 `inferred` 就是告诉读者"这一环是推断"。
  报告里可以给一个置信度（靶场二的 IDOR 就是 **0.55** 而不是 0.9，
  `ranges/README.md:29-33`：「靶场一的证据是**在场证明**，
  靶场二的是**缺席证明**」）。
- **追问 2**：「链是怎么组装的？规则写死的吗？」
  → 规则引擎，按"某漏洞产出 → 另一漏洞需要的输入"匹配。
  **是启发式的，会漏也会多**。现在没有公开的精度数字。
- **追问 3**：「如果两条链共享一个节点呢？」
  → DAG 支持，`parent_node_id` 可以有多个节点指向同一父节点。
  前端用 dagre 排版，对四类脏数据都有防御
  （`topology/layout.ts:206-252`：重复 id、自环、悬挂 parent、重边）。

# 卡片 6 · 数据模型（15 张表）与"不建边表"

### ① 一句话
**15 张表；攻击链的边不单独建表，用节点自引用派生。**

### ② 为什么需要它
报告要**可复现**：所有结论必须落库，而且能追溯到当时的状态。

### ③ 这个项目里怎么做的
15 张表（`models/__init__.py:20-37`），一个初始迁移 `3193e02f45bd`。

| 表 | 用途 |
|---|---|
| `users` / `projects` / `assessments` | 主体三件套 |
| `assessment_stages` | **断点续跑的依据**（五阶段状态与产出快照） |
| `vulnerabilities` / `taint_paths` / `poc_attempts` / `patches` | 漏洞四件套 |
| `attack_chains` / `attack_chain_nodes` | 攻击链 |
| `reports` / `resource_metrics` / `audit_logs` | 产物与观测 |
| `sandbox_configs` / `llm_configs` | 配置 |

### ④ 代码长什么样

**`taint_paths` —— 污点每一跳都落库**（`models/vulnerability.py:91`），
前端的"污点传播步进标记"就是读它。

**`attack_chain_nodes` 的自引用**（`models/chain.py:54-57`）：
```python
    parent_node_id: Mapped[int | None] = mapped_column(
        ForeignKey("attack_chain_nodes.id", ondelete="CASCADE"), nullable=True
    )
```

**`llm_configs` 表没有 `api_key` 列**（`models/llm.py:18-30`）——
只有 `provider`/`base_url`/`model`/`temperature`/`max_tokens`/`timeout_seconds`/`max_retries`/`is_default`。
文件头写：**「⚠️ API Key 不入库：只从 `.env` 的 `DEEPSEEK_API_KEY` 读取」**。

### ⑤ 为什么不那样做
- **不建边表**：见卡片 5。
- **API Key 不入库**：避免**随数据库备份泄露**（`core/config.py:101` 原文）。
  入库的话，一次 mysqldump 就把 key 带走了。
- **不给审计日志开写接口**（`api/v1/audit.py:3-5`）：
  「给它开一个手动补一条的接口，**等于让被审计者自己填证据**」。

### ⑥ 踩过的坑
**`eager_defaults` 必须显式设 True**（`db/base.py:27-47`）：

> 实际症状（2026-10-16 实测）：`POST /api/v1/projects` 返回 500……
> **报错位置与病因隔了三层**。

（SQLAlchemy 异步下，默认值的加载会触发一次隐式 IO，
在非 greenlet 上下文中直接炸 `MissingGreenlet`。同类问题还有
`assembler.py:111-115`：用显式 `select` 而不是 `session.get()`，
因为 `get()` 命中身份映射时**不发 SQL**，随后访问未加载的属性就会触发懒加载。）

### ⑦ 面试会怎么问
> 「攻击链的边为什么不建表？」

### ⑧ 你怎么答（带数字）
**三个理由，按重要性排**：

1. **结构上消除一类脏数据**：边表可能指向不存在的节点（悬挂边）。
   自引用外键 + `ondelete="CASCADE"`，**这种状态不可能出现**。
2. **数据量**：节点数远少于边数（一条 n 节点的链最多 n-1 条边，
   但实际是树/DAG，实际边数接近 n）。一张表 vs 两张表。
3. **查询模式**：前端要的是"这条链的所有节点 + 父子关系"，
   一次查节点表就够了，不用 join。

**数字**：15 张表、1 个迁移（`3193e02f45bd`）、
攻击链相关的只有 2 张（`attack_chains` + `attack_chain_nodes`）。

### 追问三层
- **追问 1**：「那查'某节点的所有子孙'怎么办？」
  → 递归 CTE，或者应用层遍历（链很短，通常 3–5 个节点）。
- **追问 2**：「为什么不用图数据库？」
  → 链的规模是**个位数节点**，图数据库的价值在深遍历和大规模。
  引一个 Neo4j 只为存 5 个节点，是纯负担（同卡片 9 的 2 vCPU 约束）。
- **追问 3**：「`taint_paths` 为什么要存每一跳，而不是只存首尾？」
  → 因为前端要**画出来**（`需求.md:26` 的"污点输入至漏洞汇聚点传播轨迹"），
  而且**面试/复核时要能逐跳核对**。只存首尾就退化成"我说有就有"。

# 卡片 7 · 权限模型（JWT + 回库重取 + 每接口独立校验）

### ① 一句话
**身份只从 JWT 取、且回数据库重读；每个写接口自己校验权限，不靠前端隐藏按钮。**

### ② 为什么需要它
这是最经典的越权漏洞来源（`需求.md` 里对应 R3）。
两个独立的问题：
- **信客户端传的角色** → 攻击者改一个字段就提权
- **只靠前端隐藏按钮** → 直接调接口就绕过

### ③ 这个项目里怎么做的
`api/deps.py`：

```
deps.py:29-57    权限点枚举（Permission）
deps.py:60-87    角色 → 权限表（ROLE_PERMISSIONS）
deps.py:98-116   get_current_user：解析 JWT → 回库重取
deps.py:123-138  require(permission)：依赖工厂，不满足抛 403
```

**三角色的写权限**：

| 角色 | 除 4 个只读外的写权限 |
|---|---|
| `security_engineer` | `assessment:create`、`vuln:review`、`report:export` |
| `developer` | `patch:accept` |
| `admin` | `sandbox:manage`、`llm:manage`、`audit:view` |

（4 个只读三角色共有：`project:view`、`assessment:view`、`vuln:view`、`report:view`）

### ④ 代码长什么样

**回库重取**（`deps.py:105-112`）：

```python
    payload = decode_access_token(credentials.credentials)   # :105
    user_id = int(payload.sub)                               # :108
    user = await session.get(User, user_id)                  # :112  ← 回库重取，以库为准
```

设计声明（`deps.py:3-7`）：
> 用户身份**一律从 JWT 解析后回库重取**，绝不采用客户端传参里的任何 `user_context` / `role`。

**依赖工厂**（`deps.py:123-138`）：

```python
def require(permission: Permission) -> Callable[..., Awaitable[User]]:
    async def _guard(user: CurrentUser) -> User:
        if permission not in ROLE_PERMISSIONS.get(user.role, frozenset()):
            raise ForbiddenError(...)          # → http_status = 403
        return user
    return _guard
```

**用法**（每个写接口各自挂）：
`projects.py:37`、`assessments.py:47`、`vulnerabilities.py:40-41`、`admin.py:39-40`、`reports.py:39`。

### ⑤ 为什么不那样做
**不做一个"全局权限中间件"按 URL 前缀判断。**
因为那样"哪个接口归哪个权限"就散在配置里，
而**新增接口时忘记登记**是静默的（接口直接可用）。

挂在函数签名上（`Annotated[User, Depends(require(...))]`），
漏了就会**类型错误**，或者说至少写接口时躲不开。

### ⑥ 踩过的坑
- **`get_optional_user` 是死代码**（`deps.py:141-152`）：定义了、docstring 说"SSE 端点用"，
  但**没有任何调用点**。SSE 实际用 `AssessmentViewer`（强制鉴权）。
  若被问"SSE 怎么鉴权"，正确答案是**标准 Bearer 头 + 强制鉴权**。
- 密码必须做 **SHA-256 预哈希**（`security.py:26-32`），
  否则超过 72 字节的口令**第 73 字节起被静默忽略**。

### ⑦ 面试会怎么问
> 「JWT 里已经签了 role，为什么还要回库重取？」

### ⑧ 你怎么答（带数字）
**因为 JWT 是无状态的，签发之后无法撤回。**

具体场景：管理员把某人从 `admin` 降成 `developer`。
- **不回库重取** → 那个人手里的旧 token 仍然写着 `role=admin`，
  在 token 过期前（**8 小时**，`core/config.py:98` `jwt_expire_minutes = 480`）
  他依然是管理员。降权**延迟 8 小时生效**。
- **回库重取** → 下一次请求就是 `developer`。

**代价**：每个请求多一次数据库查询。这个项目接受它 ——
因为连接池只有 2（卡片 15），查询很轻，而且**权限正确比省一次查询重要**。

**再加一条**：全库 grep `user_context` / `payload.role` / `body["role"]`，
**唯一命中是 `deps.py:4` 那句注释本身** —— 即"不许这么做"的那句话。
方向是反的：`auth.py:48` 的 `role=user.role.value` 是**从库里的 user 写进 token**。

### 追问三层
- **追问 1**：「那 JWT 里为什么还要放 role？」
  → 前端用它渲染菜单/按钮（少发无用请求）。但**后端不信任它**。
- **追问 2**：「`require` 返回 403 的链路是什么？」
  → `_guard` 抛 `ForbiddenError`（`exceptions.py:124-128`，`http_status=403`）
  → 被 `core/response.py:37-43` 的 `app_error_handler` 渲染成
  `{detail, error:{...}}` 结构。
- **追问 3**：「CVE/漏洞的复核操作，谁能做？」
  → `vuln:review` → 只有 `security_engineer`。
  `developer` 只有 `patch:accept`（采纳补丁），**不能复核漏洞**。
  这个划分对应 `需求.md:16-18` 的三角色职责。

# 卡片 8 · SSE 实时日志（为什么不用 EventSource）

### ① 一句话
**用 `fetch` + `ReadableStream` 手写 SSE，因为 `EventSource` 不能设请求头，
只能把 JWT 塞进 URL —— 而那会泄露凭证。**

### ② 为什么需要它
评估要跑几十秒，用户要看到实时进度。轮询浪费且延迟高，SSE 是正解。

### ③ 这个项目里怎么做的
后端：`api/v1/assessments.py:298-371`，日志写 Redis Stream，
SSE 端点按 `Last-Event-ID` 补读。
前端：`frontend/src/api/useLogStream.ts`。

### ④ 代码长什么样

**为什么要手写**（`useLogStream.ts:1-10` 原文）：

```
 * 刻意不用 `EventSource`：它无法设置请求头，只能把 JWT 塞进 URL 查询串，
 * 而查询串会被 nginx access log、浏览器历史、Referer 记录 —— 等于泄露凭证。
 * 这里用 `fetch` + ReadableStream 手动解析 SSE，从而能用 `Authorization` 头。
 *
 * 断线重连时回传 `Last-Event-ID`，后端从 Redis Stream 的该 ID 之后重放，
 * 保证断线期间不丢日志（总纲 §6.2）。
```

**指数退避**（`useLogStream.ts:166-171`）：

```ts
// 指数退避重连，最多 10 次；重连时靠 Last-Event-ID 补回断线期间的日志
if (retry < 10) {
  const delay = Math.min(1000 * 2 ** retry, 15_000)   // 1s→2s→4s…封顶 15s
  retry += 1
  timer = setTimeout(() => void connect(), delay)
}
```

**游标必须在过滤之前推进**（`useLogStream.ts:150-153`）——
先记录"读到哪了"，再决定"这条要不要显示"。反过来的话，
被过滤掉的日志会让游标停滞，重连时**重复拉取**。

### ⑤ 为什么不那样做
- **不用 `EventSource`**：上面的凭证泄露问题。
- **不用 WebSocket**：只需要服务端→客户端单向推送，
  WebSocket 是双向的，多一套协议和心跳。
- **不用轮询**：延迟高、请求多。

### ⑥ 踩过的坑
**SSE 连接不能挂在请求级会话上**（`assessments.py:377-379`）：

> SSE 连接可以持续几十分钟，把会话挂在这条流上等于**让一个数据库连接被长期占用**。

（这段注释写"池子只有 5 个"，**实际配置是 2** —— 注释过期了。）

**另一个坑**：`Last-Event-ID` 不传 → 断线重连后中间日志**永久丢失**，
而且**没有任何提示**。

### ⑦ 面试会怎么问
> 「SSE 你用的 `EventSource` 吗？」

### ⑧ 你怎么答（带数字）
**不是，是 `fetch` + `ReadableStream` 手写解析。** 理由是安全问题：

`EventSource` 的 API **不支持自定义请求头**。要用它，就只能
`new EventSource('/api/v1/assessments/1/logs?token=xxx')`——
**JWT 进 URL 查询串**，而查询串会进：
① nginx access log ② 浏览器历史 ③ `Referer` 头（跳到外链时带上）。

**等于把凭证写进了三个会持久化的地方。**

手写解析的代价是**要自己按 `\n\n` 切帧**（`useLogStream.ts:135-157`
用 `res.body.getReader()` + `TextDecoder`），
但换来了 `Authorization: Bearer` 这个标准位置。

**数字**：退避 `1s → 2s → 4s → … → 封顶 15s`，最多 **10 次**。

### 追问三层
- **追问 1**：「手写解析容易出什么问题？」
  → ① 一个帧可能跨多个 chunk（要缓冲）② 多字节 UTF-8 字符可能被
  chunk 切断（`TextDecoder` 要设 `stream: true`）③ 游标推进时机。
  第三条踩过，见上面。
- **追问 2**：「断线重连怎么保证不丢日志？」
  → 客户端回传 `Last-Event-ID`（`assessments.py:308` 读它），
  后端从 Redis Stream 的该 ID 之后补读（`:317-322`）。
  **Redis Stream 支持按 ID 范围读**，这是选它而不是 Pub/Sub 的原因之一
  （Pub/Sub 是即发即弃的，断线期间的**消息永久丢失**）。
- **追问 3**：「为什么不用 Redis Pub/Sub？」
  → Pub/Sub **不持久化**。断了就丢，无法 `Last-Event-ID` 补读。
  Stream 是**可回放的**。代价是 Stream 会累积，要设 `MAXLEN` 或定期裁剪。

# 卡片 9 · 五阶段编排与容错分级

### ① 一句话
**五个阶段顺序跑；哪些失败能继续、哪些必须整个失败，声明在 Agent 类上而不是引擎里。**

### ② 为什么需要它
**验不了 ≠ 没问题。** 沙箱连不上就不出报告，等于把"基础设施故障"
变成了"这个项目很安全"—— 最糟的失败模式。

### ③ 这个项目里怎么做的
`recon → code_audit → poc_verify → exploit_chain → report_gen`

| 阶段 | 容错档 | 失败后 |
|---|---|---|
| recon / code_audit / report_gen | `FATAL` | 整个评估 `failed` |
| poc_verify / exploit_chain | `SKIPPABLE` | 阶段标 `skipped`，**继续** |

### ④ 代码长什么样

**档位声明在 Agent 类上**（`agents/base.py:53-61`）：

```python
class FaultTolerance(StrEnum):
    #: 失败 → 整个评估 `failed`。`recon` / `code_audit` / `report_gen` 属此档
    FATAL = "fatal"
    #: 失败 → 阶段标 `skipped`，**后续阶段继续**。`poc_verify` / `exploit_chain` 属此档
    SKIPPABLE = "skippable"
```

**为什么不在引擎里写 if**（`agents/base.py:15-17`）：

```python
# 但把那张表写成 `engine.py` 里的 `if stage in (POC_VERIFY, EXPLOIT_CHAIN)`，
# 就又回到「引擎里散落阶段名」了。改成在 Agent 类上声明 `fault_tolerance`：
# **引擎仍然按阶段决策（它只是读一个属性），而档位的归属回到了离它最近的模块**。
```

### ⑤ 为什么不那样做
**不做"所有阶段都 FATAL"** —— 那会让沙箱故障毁掉整个评估。
**不做"所有阶段都 SKIPPABLE"** —— 那会让 `code_audit` 失败后
仍然出一份空报告（最坏的失败模式）。

### ⑥ 踩过的坑
**`engine.py` 曾经 import 了一个从不存在的名字**
（`test_import_integrity.py:1-27` 记录）：

> `engine.py::_default_sandbox_provider` 写了
> `from app.sandbox.service import get_sandbox`，而该名字**从未被写出来过**，
> 导致 `poc_verify` **永远静默降级**。

**为什么没被发现**：那是**惰性 import**（在函数体内），
失败被 `except` 吞掉 → 降级 → 阶段标 `skipped` → **状态是 `completed`**。

所以有了 `test_import_integrity.py`：
用 AST 扫所有 `from app.X import Y`，**逐个验 `Y` 真的存在**。

### ⑦ 面试会怎么问
> 「某个阶段失败了怎么办？」

### ⑧ 你怎么答（带数字）
分两档，判据是**"后续阶段还有没有可用输入"**：

- **FATAL（3 个）**：`recon`（没技术栈就没法审计）、
  `code_audit`（没漏洞集合报告就是空的）、
  `report_gen`（交付物本身）。
- **SKIPPABLE（2 个）**：`poc_verify`、`exploit_chain`。
  理由一句话：**「没验证出来」不等于「不存在」，
  静态分析的成果不该因为沙箱连不上而作废。**（`agents/base.py:59-60`）

**关键细节**：`poc_verify` 失败时，漏洞**保持 `unverified`**，
**不会被标成 `rejected`**。"没验"和"验了没问题"是两件事。

### 追问三层
- **追问 1**：「阶段状态和评估状态是什么关系？」
  → 评估状态：`created`/`running`/`completed`/`failed`/`stopped`。
  阶段状态独立记录在 `assessment_stages` 表。
  **一个 `completed` 的评估里可以有 `skipped` 的阶段** ——
  这正是要避免"静默失败"的地方。
- **追问 2**：「怎么知道该不该信这份报告？」
  → 看阶段状态 + 报告里的 `degraded` 列表。
  `poc_verify` 是 `skipped` → 所有漏洞都是 `unverified`，报告会说明。
- **追问 3**：「新增第 6 个阶段要改哪里？」
  → ① 继承 `BaseAgent` ② 登记 `stage` ③ 在 `registry.py` 绑定。
  **`engine.py` 一行不用改**（`agents/base.py:5-8`）。

# 卡片 10 · 断点续跑与"阶段边界是唯一提交点"

### ① 一句话
**事务只在阶段与阶段的交界处提交；Agent 不许自己 commit。**

### ② 为什么需要它
要能断点续跑，就必须有一个**干净的断点**。
如果阶段内随意提交，崩了之后库里是"部分成功"的中间态，**没有正确的续跑点**。

### ③ 这个项目里怎么做的
- `db/session.py:45-56` `get_session()` 是 async generator，**不在依赖里 commit**
- `agents/base.py:73` `session` 走构造函数注入，注释「**Agent 不得 commit**」
- 每阶段产出连同快照落 `assessment_stages`

### ④ 代码长什么样

`db/session.py:48-49` 的 docstring：

```python
    """……**不在依赖里 commit**：提交点由业务代码显式控制……
    隐式提交会让「部分成功」的中间态落库，破坏断点续跑。
    """
```

**为什么 session 走构造函数注入**（`agents/base.py:21-30`）：

```python
# T4 定的是「阶段边界是唯一原子提交点」—— 阶段内不得提交。所以 Agent 写库
# 必须用**引擎持有的那个 session**，由引擎在阶段结束时统一 commit。
# 如果把 session 塞进 `run` 的参数或者放进 `ctx`（像 `sandbox_handle` 那样），
# 前者改了签名，后者往一个会被序列化的载体里塞不可序列化的东西。
```

### ⑤ 为什么不那样做
**不用 `asyncio.Task.cancel()` 停止评估**（`orchestrator/cancel.py:3-6`）：

> 它会在**任意** `await` 点抛出 `CancelledError`，而阶段执行里有大量 await
> 落在数据库事务中间。恰好在那里被中断的后果是
> 「`Finding` 提交了、它的 `TaintPath` 没提交」—— **孤儿记录**。

改成**协作式取消**：写 Redis 标志位，引擎在**阶段边界**检查（`engine.py:216-220`）。

### ⑥ 踩过的坑
**`ctx` 会被序列化** —— 所以任何放进去的东西都必须可序列化。
一个数据库 session 显然不是。这条约束解释了为什么依赖走构造函数。

**另一个**：`_vuln_id` 退化成 0（`test_poc_verify_id_seam.py:1-23`）——
`Finding` 没带真实主键 → 探针跑了但结论没落对地方 → 全 `unverified`，
**而阶段状态仍是 `completed`**。docstring 写：「**失败是静默 + 状态正常**」。

### ⑦ 面试会怎么问
> 「怎么做到断点续跑？」

### ⑧ 你怎么答（带数字）
**关键是"断点要干净"**：

1. **提交点唯一**：只在阶段边界 commit（T4）。所以崩了之后，
   要么某阶段的产出**全在**，要么**全不在** —— 不存在"扫了一半"。
2. **断点就是阶段**：`assessment_stages` 表记五个阶段各自的状态与产出快照。
   重启后从第一个非完成阶段开始。
3. **取消也不切断事务**：用 Redis 标志位 + 阶段边界检查，
   而不是 `Task.cancel()`。

**代价要说清**：长命令（比如容器里跑一个 30 秒的探测）
**要等它自己超时**才能响应取消。这是**刻意接受的** ——
宁可慢，不要孤儿记录。

### 追问三层
- **追问 1**：「那阶段内部失败了，半天的扫描白做了？」
  → 是的，整个阶段重来。这是**用时间换正确性**。
  可以优化（阶段内做检查点），但会重新引入"部分成功"的问题。
- **追问 2**：「`ctx` 里到底放了什么？」
  → 评估上下文（技术栈、工作区句柄等），要落库供续跑。
  所以 `AgentDeps` 用 `frozen=True, slots=True`，
  「往上面挂一个临时属性」在运行时**直接报错**。
- **追问 3**：「如果提交到一半数据库挂了？」
  → 整个阶段的 commit 是原子的（单个事务），要么全成功要么全回滚。
  回滚后评估状态是 `running` 但阶段未完成 → 重启后重跑该阶段。

# 卡片 11 · 评测体系（GROUND_TRUTH 是"量具"）

### ① 一句话
**两个靶场 + 逐行钉死的标准答案 + 一个能算出召回率和误报数的脚本。**

### ② 为什么需要它
"我的工具能扫漏洞" —— **这句话没有数字就是空的**。
而"我们做了很多测试"也不等于评测：测试验证的是"代码符合我的预期"，
评测验证的是"**我的预期对不对**"。

### ③ 这个项目里怎么做的
```
ranges/ecommerce/     11 个植入漏洞，521 行
ranges/usercenter/     4 个植入漏洞（+1 条载体），266 行
ranges/*/GROUND_TRUTH.yaml   每个漏洞钉死 file + line_start + line_end
backend/tests/benchmark.py   拿扫描结果对答案
```

**行号怎么来的**（`GROUND_TRUTH.yaml:8-9`）：

> `line_start` / `line_end` 取自 `app.analysis.analyze_project()` 的**实际输出**
> （配合 `ast` 的 `end_lineno` 核对语句边界），**不是照着源码数出来的**。

### ④ 代码长什么样

**匹配判据三条全中**（`benchmark.py:127-133`）：

```python
def _relates(entry, finding) -> bool:
    if _category_of(finding) != entry.category:   # 类别字面值，不归一化
        return False
    if Path(...).name != entry.file:              # 只比 basename
        return False
    return entry.covers(int(getattr(finding, "line_start", 0) or 0))
```

**误差窗口 ±2 行**（`benchmark.py:59,73-75`）：

```python
LINE_WINDOW = 2
...
def covers(self, line: int) -> bool:
    return self.line - LINE_WINDOW <= line <= self.line_end + LINE_WINDOW
```

### ⑤ 为什么不那样做
- **不比绝对路径，只比 basename**：因为工作区路径每次不同。
- **类别不归一化**：故意 —— 归一化会**掩盖类别判断错误**。
- **`--dynamic` 刻意不实现**（`benchmark.py:238-262`）：
  动态验证要 `Sandbox` + `WorkspaceHandle`，而 workspace 绑在数据库实体上。
  引 DB 会毁掉这个脚本「**分母来自 GROUND_TRUTH.yaml、跑起来不需要任何外部依赖**」
  的立身之本。

### ⑥ 踩过的坑（这是最值得讲的一个坑）

`ranges/README.md:78-96`：

> **改靶场里的一行代码，等于把量具的刻度磨掉一格。**
> ……**净增 3 行就能让后面所有基准条目失配**。
>
> 踩过一次，代价很具体：给 `ranges/ecommerce/app.py` 的 docstring 补了 5 行说明，
> 召回率从 **11/11 掉到 3/11、误报 8**。**代码一行没改，坏的是基准。**

**注意"代码一行没改，坏的是基准"** —— 系统表现变差了，
但**被测对象没变，变的是尺子**。

### ⑦ 面试会怎么问
> 「你怎么衡量这个系统的效果？」

### ⑧ 你怎么答（带数字）

**硬数字**（我实跑 `uv run python tests/benchmark.py`）：

| | 召回 | 误报 |
|---|---|---|
| ecommerce | **11/11 (100%)** | 0 |
| usercenter | **3/5 (60%)** | 0 |
| **合计** | **14/16 (87.5%)** | **0** |
| 其中 PRD §10 指定的 8 条 | **7/8 (87.5%)** | — |

**然后主动交代那两条漏的**（**这段是加分项，一定要说**）：

`usercenter` 漏的两条（V7 手机号未脱敏、V8 调试接口本身），
在 `GROUND_TRUTH.yaml` 里**自己标了 `detectable: none`**。

**不是忘了写规则，是这两类问题在原理上静态查不出来**：

- **V7「该脱敏没脱敏」** —— 既不是数据流问题（数据流是干净的），
  也无法在单次请求里证明（要对比"有权限的人看到什么"和"没权限的人看到什么"）。
  它需要一个**合规要求**才能判定，而系统没有这个输入。
- **V8 调试接口本身** —— 没有任何规则能说"这个端点不该存在"。

**为什么还是登记进基准**（V7 的 note 原文）：

> 如实登记在这里，是为了让「**V7 漏了**」这个结论**出现在基准里，
> 而不是消失在分母外**。

**这句话是整个评测体系里最值钱的一句。**
一个只统计"能查出来的"的基准，召回率永远是 100%。

**再加一个 V8 的细节（半命中）**：
V8 的调试接口**本身**查不出来，但它**借道 `settings.py` 的硬编码密钥**被间接命中了 ——
因为 `hardcoded_secret` 在 `canonical_vuln_type` 里归一到 `info_disclosure`，
而这个类型会驱动 `read_config` 探针去打 `/debug/config`。
所以**静态给了线索，动态在真实端点上确认了**。

### 追问三层
- **追问 1**：「87.5% 算好吗？」
  → 分母只有 16，**样本太小，谈"好"没有意义**。
  这个数字的价值是**可复现的基线** —— 改了引擎，跑一遍就知道有没有退化。
  **不是**一个可以和别人比的 benchmark 分数。
- **追问 2**：「误报 0，是不是因为规则写得太保守？」
  → **部分是**。这正是"报多与漏代价不对称"那个取舍的体现（卡片 2）。
  但 0 误报在 16 个样本上也不说明什么 —— 真实工程上误报率
  **没量过**，因为我们只有靶场。
- **追问 3**：「动态验证那一步的效果呢？剔掉了多少误报？」
  → **没有数字，因为 `--dynamic` 没实现**。诚实答"没量过"，
  然后说明为什么：脚本刻意不依赖数据库。
- **追问 4（可能追问到这）**：「那你改了引擎怎么知道没退化？」
  → 跑 `benchmark.py`。但**前提是别动 `ranges/`** ——
  动过之后 11/11 掉到 3/11 那次事故，就是因为改了量具。

  → **探针路由**。因为它决定了这个系统在真实工程上"能不能用"——
  其余缺陷是"不够好"，这一条是"用不了"。
- **追问 3**：「`resource_metrics` 那个，最简单的修法是什么？」
  → 在 worker 启动时 `MetricsSampler.start()`。
  但**不能直接加** —— 要先决定采样数据写在哪一层
  （写在 B2 编排层还是 B3 沙箱层，决定了它能不能拿到容器指标）。
  这是个设计问题，所以有那份专门的文档。

# 卡片 13 · LLM 降级链与补丁三态

### ① 一句话
**LLM 不可用不是异常，是设计内的正常路径 —— 降级到模板，并且让用户看得出来。**

### ② 为什么需要它
没有 key 的开发环境、网络抖动、模型限流 —— 这些**每天都会发生**。
如果每次都要报错，系统就没法在没配 key 的环境里跑。

### ③ 这个项目里怎么做的

**降级原因的枚举**（都是明确的值，不是自由文本）：
`no_api_key` / `budget_exceeded` / `guard_rejected` / `not_a_diff`。

**两道闸**（`llm/expressions.py:32-37`）：
- 报告层总预算 **20 秒**（`DEFAULT_BUDGET_SECONDS = 20.0`）
- 并发 **4**（`DEFAULT_CONCURRENCY = 4`）

**为什么要有预算**：报告里有 N 条漏洞，每条都要调一次 LLM。
不设上限的话，一份 50 条漏洞的报告会调 50 次 LLM ——
**报告生成 ≤30s 这个指标就没了**。

### ④ 代码长什么样

**四个用点的降级结构完全一样**（`llm/expressions.py:124-128` 附近）：

```python
    try:
        ... 调 LLM ...
    except Exception as exc:            # noqa: BLE001 —— 按 L4，捕获一切
        return _degrade(...)            # 转模板，reason 记录原因
```

**降级日志用 INFO 不是 WARNING**（`expressions.py:73-76` 的注释）——
因为降级是设计内的正常路径。

**批量的两条短路**（`expressions.py:303-325`）：
- 未配 key → 在批量层就短路（`reason="no_api_key"`），**根本不发请求**
- 超预算 → `reason="budget_exceeded"`

**补丁的三态**（`frontend/src/api/types.ts:45`）：

```ts
export type PatchSource = 'llm' | 'template' | 'validate_failed'
```

前端**必须视觉区分**（`PatchSection.tsx:9-13`）：**绿 / 蓝 / 红**，
注释写「**绝不能长成一个样子**」。

### ⑤ 为什么不那样做
- **不重试到成功**：重试只会让报告生成时间不可控。
  重试只发生在 HTTP 层对**可重试状态码**（`{408,409,425,429,500,502,503,504}`）
  和畸形响应，最多 **1 次**（`client.py:158`，`llm_max_retries=1`），
  退避 **0.5s**（线性）。
- **不把降级当异常抛给调用方**（`llm/__init__.py:25-26`）：
  「一律降级，**不抛异常给调用方**」。

### ⑥ 踩过的坑
**`validate_failed` 这个状态是最有价值的一个。**

它表示：**模型产出了补丁，但没过第四道校验**
（打完补丁重跑污点引擎，发现污点路径还在）。

**为什么必须有这个态**：如果只有 `llm` / `template` 两态，
那"模型生成的不合格补丁"会被当成 `llm` 展示 —— 用户会**照着一个没用的补丁去改代码**。
`validate_failed` 用红色告警明确说"这个不能用"。

**另一个坑**：`page.pdf()` 不接受 `timeout` 参数（`report/pdf.py:39-47`），
传进去抛 `TypeError`，而且**只在真的导出 PDF 时才暴露**。

### ⑦ 面试会怎么问
> 「LLM 挂了怎么办？」

### ⑧ 你怎么答（带数字）
**四个用点全部降级为确定性模板，报告照常产出，只有措辞变差。**

具体：
- 降级模板在 `llm/fallback.py`，**437 行** ——
  这个文件本身就说明"可降级"是**一等公民**，不是补丁。
- **降级不抛异常**（L4），调用方拿到的永远是可用的文本。
- **用户看得出来**：报告里有 `degraded` 列表；补丁有 `source` 三态，
  前端**绿/蓝/红**区分。

**数字**：LLM 调用超时 **15s**、最多 **2 次尝试**（首次 + 1 次重试）、
退避 **0.5s**；报告层总预算 **20s**、并发 **4**。

**关键一句**：降级**不影响结论**。这句话有测试
（`test_llm_fallback.py` 等 5 个文件）。

### 追问三层
- **追问 1**：「模板降级出来的文案，用户能接受吗？」
  → 比模型差，但**准确、可复现、不含幻觉**。
  而且模板**不允许出现占位符**：
  `test_llm_fallback.py:159` 有个 `_FORBIDDEN` 元组，
  禁止 `TODO`/`{`/`}`/`None`/`undefined`/`placeholder` 出现在模板产物里。
  （`fallback.py:9` 文件头也写：「**不出现占位符**：没有 `TODO`、
  没有 `{未知类型}` 这种糊弄」。）
- **追问 2**：「20 秒预算超了之后呢？剩下的漏洞怎么办？」
  → 剩下的直接用模板（`reason="budget_exceeded"`），
  **不是"不生成"**。报告仍然是完整的。
- **追问 3**：「为什么不缓存 LLM 结果？」
  → 现在没做。做的话要小心：**缓存 key 必须包含全部输入**
  （漏洞内容 + 已判定的事实），否则改了代码却命中旧缓存，
  会产出**和当前结论不符的文案**。那比不缓存更糟。

# 卡片 14 · 报告的确定性评分与排序

### ① 一句话
**安全分、等级、清单顺序、整改优先级 —— 全是纯函数算的，一行 LLM 都没有。**

### ② 为什么需要它
如果排序由模型决定，**同一份数据两次生成会得到两份不同的报告**。
而报告是交付物，必须可复现。

### ③ 这个项目里怎么做的
`report/scoring.py`（374 行纯函数）：

| 函数 | 算什么 |
|---|---|
| `chapter3_sort_key` (`:282-287`) | 第 3 章漏洞清单顺序 |
| `priority_of` (`:308-328`) | 单条整改建议的优先级 |
| `rank_recommendations` (`:331-347`) | 第 5 章整改顺序 |

装配时用它们排序（`assembler.py:203,224`）。

### ④ 代码长什么样

`scoring.py:1-6` 文件头：

```python
"""……**全部是纯函数，没有一行 LLM**……项目综合等级、`security_score`、
第 3 章清单顺序、**第 5 章的整改顺序** —— 全部由这里的确定性公式产出。
LLM 只写第 5 章的文案，**既不打分、也不排序**。
"""
```

**修复成本以倒数进入公式**（`scoring.py:308-317`）：

```python
    # 修复成本以倒数进入公式，这是对设计文档字面写法的一处**刻意收紧**：
    # 若按字面直接 `× 成本`，语义会反过来……所以这里用 `1/成本`
```

### ⑤ 为什么不那样做
**不按 CVSS 单一排序。** 整改优先级要综合考虑
严重度、**修复成本**、是否在攻击链上 —— 所以 `priority_of` 是个多因子函数。

**不让 LLM 参与排序**（`prompts.py:205-209`）：

> ⚠️ **`rank` 是输入，不是输出。**……顺序一旦由模型决定，
> 同一份数据两次生成就会得到两份不同的报告。

### ⑥ 踩过的坑
**`rank` 作为输入喂给模型**（`prompts.py:205`）——
这是一个容易搞反的地方：模型**知道**这是第几条，才能写出
"这是最高优先级的整改项"这种话，但它**不能决定**谁是第一条。

**"× 成本" vs "÷ 成本"**：设计文档字面写的是 `× 成本`，
但那样语义会反过来（成本越高优先级越高）。代码里**刻意收紧**成 `1/成本`
（`scoring.py:308-317`）。这是一个"敢于偏离文档"的例子。

### ⑦ 面试会怎么问
> 「安全评分怎么算的？」

### ⑧ 你怎么答（带数字）
**确定性公式，在 `report/scoring.py`（374 行纯函数）**：
- 输入：漏洞的 CVSS、状态（`verified` / `potential` 权重不同）、
  是否在攻击链上、修复成本；
- 输出：`security_score` + 综合等级（极高危/高危/中危/安全）+ 两个排序。

**为什么强调"纯函数"**：纯函数意味着**同样的输入永远同样的输出**，
可以单测、可以在报告里复现、可以和上一次对比。

**数字**：`scoring.py` **374 行，没有一行 LLM**；
靶场实测的一次评估：**高危 82.40 分**（usercenter，5 条漏洞）。

### 追问三层
- **追问 1**：「`potential` 和 `verified` 在评分里权重差多少？」
  → 具体权重在 `scoring.py` 里，是个显式常数。
  **设计意图**：`potential` 计分但打折，因为"未确认"不等于"不存在"。
- **追问 2**：「修复成本怎么估的？」
  → 按漏洞类型 + 影响面。**这是个启发式估计，不精确** ——
  但比"按 CVSS 一刀切"更接近实际整改决策。
- **追问 3**：「如果两条整改项分数一样呢？」
  → 需要**稳定的 tie-breaker**，否则排序不稳定（同样输入两次跑出不同顺序）。
  这是纯函数设计里必须处理的一个细节。

# 卡片 15 · 基础设施约束（连接池 2 与 SSH 隧道）

### ① 一句话
**连接池取 2 不是 5 —— 因为瓶颈是 SSH 隧道的通道数，不是数据库。**

### ② 为什么需要它
本机没 Docker、没有 MySQL/Redis。所有中间件在远端 ECS 上，
而安全组把 3306/6379 挡在公网外（**那台机器曾因数据库暴露公网被勒索**）。

所以必须走 SSH 隧道。而隧道的通道数是**有限的**。

### ③ 这个项目里怎么做的
`deploy/tunnel.py`（414 行）把 ECS 的 MySQL/Redis 映射到本机
**13306 / 16379**（刻意避开 3306/6379）。

**连接池 = 2**（`core/config.py:45-60`）：

> ECS 的 sshd `MaxSessions` 默认 **10，且按"通道"计而不是按"客户端"计** ——
> 每条经隧道的 MySQL 连接占一条通道，**API 与 worker 共享这 10 条**。
> 取 5 时一个进程的上限是 `pool_size(5) + max_overflow(5) = 10`，
> 一个进程就能吃满全部通道；两个进程一起跑必然超限。
> 取 2 ⇒ 每进程上限 4 条，两个进程共 8 条，给隧道自身的 SSH 连接留出余量。

### ④ 代码长什么样

`db/session.py:24-33`：

```python
engine: AsyncEngine = create_async_engine(
    settings.mysql_dsn,
    pool_size=settings.mysql_pool_size,       # 默认 2
    max_overflow=settings.mysql_pool_size,    # 也等于 2 → 上限 4
    pool_pre_ping=True,
    pool_recycle=1800,
)
```

**隧道超限时不能关连接**（`deploy/tunnel.py:139-143`）：

```python
# 那条连接上**其它健康的通道正被别处用着**，
# 把它关掉等于让一次超限变成一次全面断连。
```

### ⑤ 为什么不那样做
- **不开安全组端口**：那台机器被勒索过，就是因为数据库暴露公网。
  隧道既解决连通性，**又不需要在安全组上再开任何口子**。
- **`pool_pre_ping` 不够**：它只能在借出连接时探测，
  **而探测本身也要走通道** —— 救不了半开的通道。

### ⑥ 踩过的坑
**取 5 时的实际症状**：健康检查在 **19 秒**后开始返回 **500**，
连接堆在 `CLOSE_WAIT`。

**`direct-tcpip` vs `request_port_forward`**（`tunnel.py:24-31`）：

> 两者名字很像，用错了报的是 `TCP forwarding request denied`……
> **错误信息指向的排查方向完全是歪的**。

（前者 == `ssh -L`，后者 == `ssh -R`。）

### ⑦ 面试会怎么问
> 「你的连接池配了多大？**为什么？**」

### ⑧ 你怎么答（带数字）
**2。而且理由不是数据库，是 SSH 隧道。**

- ECS 的 sshd `MaxSessions` 默认 **10**，**按通道计不按客户端计**；
- 每条 MySQL 连接占一条通道，API 和 worker **共享这 10 条**；
- 取 5 ⇒ 单进程上限 `5 + 5 = 10`，**一个进程就吃满**，
  两个进程必然超限；
- 取 2 ⇒ 单进程上限 4，两进程共 8，**留 2 条给隧道自己**。

**实际症状**：取 5 时健康检查 **19 秒后开始 500**，连接堆在 `CLOSE_WAIT`。

**加分**：`pool_pre_ping=True` 在这**救不了** ——
它只能在借出连接时探测，而探测本身也要走通道。

### 追问三层
- **追问 1**：「为什么不用连接池更大的本地方案？」
  → 本机没有 MySQL/Redis（只有那台 ECS 有 Docker）。
  这是**环境约束**，不是设计选择。
- **追问 2**：「那并发上不去怎么办？」
  → 并发**本来就恒为 1**（2 vCPU，`概要设计总纲.md:579`）。
  所以连接池 2 是**够的** —— 它不是瓶颈，是恰好匹配。
- **追问 3**：「生产环境要怎么改？」
  → 数据库和应用同机部署（或走内网），就**不再受隧道通道数限制**，
  可以按实际并发配池子。现在的 2 是**开发态拓扑的产物**。
