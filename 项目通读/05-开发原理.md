# 05 · 开发原理

**这份文档讲的是"这个项目反复出现的做事规矩"。**

每条规矩都按同一个格式：**规矩 → 为什么 → 不守会出什么事 → 代码里的落点**。

> 第四栏最重要。**每条规矩背后都有一个真实事故**，不是"最佳实践"抄来的。
> 面试时讲事故比讲原则有说服力得多。

---

## 原理 1 · 三条硬边界（分层铁律）

### 规矩

| 边界 | 内容 |
|---|---|
| **`analysis/` 不许 import `db/`、`llm/`、`fastapi`、`orchestrator/`** | 引擎必须能脱离数据库和网络单独跑 |
| **领域引擎层不许 import FastAPI** | `verify/`、`chain/`、`report/` 里出现 `from fastapi import ...` 就是错的 |
| **`api/` 不许写业务逻辑和 SQL** | 只做校验 + 权限 + 转发 |

### 为什么

第一条是**可测试性**：如果污点引擎 import 了数据库 session，
那测一条规则就得先起一个 MySQL。而现在 `test_taint_engine.py` 可以直接喂源码字符串。

第二条是**可替换性**：换个 Web 框架（或者包一层 CLI），领域引擎一行不用改。

第三条是**防越权**：权限校验若散落在业务函数内部，"某个接口忘了校验"就查不出来。
放在 `api/` 这一层，可以逐个文件核对。

### 不守会出什么事

**不是"架构不优雅"，是"结论不再可信"**：
一旦引擎能拿到数据库，下一个人就会忍不住从库里读一个"上次的结论"来用 ——
那时"同一份代码跑两遍结论一样"这个保证就没了。

### 代码里的落点

这个边界**有测试守着**（`backend/tests/test_taint_determinism.py`）：
它用 AST 扫 `app/analysis/` 的所有源码，断言**没有** import
`app.llm` / `app.db` / `fastapi` / `app.orchestrator`。

> **docstring 写得很直接：「红线一旦被越过，测试先红。」**
> 这是把一条架构约定变成**机器可验证的事实** —— 比写在文档里强得多。

## 原理 2 · 唯一真相（同一个语义只准有一份实现）

### 规矩

跨模块共用的逻辑，**必须指明它归谁**，不许两边各写一份。

### 不守会出什么事

`模块间契约.md` 里举的是这个例子：

> 登录时算出的 `effective_depts` 与依赖注入时算出的不一样 ——
> **最难查的越权/漏权 bug**。

两边各自实现，平时都对；某天有人在其中一边加了一个边界条件，
于是**同一个用户在两处有不同的权限**。这类 bug 不会崩、不会报错、测试也大概率是绿的。

### 代码里的落点

**阶段顺序 `STAGE_ORDER`**：`engine.py` 只遍历它，五个 Agent 的容错档位
声明在各自的类上（`agents/base.py:53-61`）。新增阶段改一处。

**漏洞类型的归一化**：`canonical_vuln_type` 是唯一把"具体规则名"
映射到"标准漏洞类型"的地方。这直接决定了探针选哪个模板 ——
见 [06-知识点精讲.md](06-知识点精讲.md) 里 V8 那个"半命中"的例子。

## 原理 3 · 阶段边界是唯一提交点（T4）

### 规矩

**Agent 不得 commit。** 事务提交只发生在阶段与阶段的交界处，由引擎统一做。

### 为什么

因为要**断点续跑**，而且"部分成功"的中间态是毒药。

`db/session.py:48-49` 的 docstring：

> **不在依赖里 commit**：提交点由业务代码显式控制……
> **隐式提交会让「部分成功」的中间态落库，破坏断点续跑**。

`agents/base.py:73` 更直接：「引擎持有的会话。**Agent 不得 commit**」。

### 不守会出什么事

想象 `code_audit` 阶段扫到第 7 个文件时崩了。如果每扫一个文件就 commit：

- 库里存着第 1–6 个文件的漏洞
- 第 7 个文件的**部分**漏洞（取决于崩在哪一行）
- 评估状态是 `running`

重启后从断点续跑 —— **从哪个断点？** 第 7 个文件已经"部分"扫过了，
重扫会重复，不重扫会缺失。**没有一个正确的选择。**

而如果只在阶段边界 commit：要么整个 `code_audit` 的产出都在，要么都不在。
断点就是**阶段**，语义干净。

### 相关：为什么用协作式取消，不用 `Task.cancel()`

同一个道理。`orchestrator/cancel.py:3-6`：

> 它会在**任意** `await` 点抛出 `CancelledError`，而阶段执行里有大量 await
> 落在数据库事务中间。恰好在那里被中断的后果是
> 「`Finding` 提交了、它的 `TaintPath` 没提交」—— **孤儿记录**。

所以停止评估是**写一个 Redis 标志位**，引擎在**阶段边界**检查
（`engine.py:216-220`）。**代价是长命令要等它超时；收益是不会切断事务。**

## 原理 4 · 降级是允许的，发明是不允许的

### 规矩

LLM 不可用、超时、输出不合格 → **一律降级为确定性模板**。
但**不许**自己改写、拼接、编造。

### 为什么

`llm/guard.py:12-16`：

> 拒收的代价已知且可控（措辞变差）；改写的代价是「我们发明了一段
> 既不是模型说的、也不是模板说的文本」，它无法解释、无法复现。

**"无法解释"是关键词**。一份安全报告里的每句话，都应该能回答
"这是从哪来的"。三种来源是干净的：① 代码算的 ② 模型说的（且通过了校验）
③ 模板写的。**第四种来源（我们临时改的）不该存在。**

### 不守会出什么事

回到精读 6 讲的那个场景：模型输出里有个编造的文件路径。
如果"聪明地"删掉那一句，文案读起来依然通顺 ——
**于是幻觉的痕迹消失了**，而剩下的文本语义可能已经错了。

### 代码里的落点

- `llm/fallback.py`（437 行）—— 「**「拿掉 LLM，结论一字不变」这句话的实际载体**」（文件头原文）
- 降级原因有明确枚举：`no_api_key` / `budget_exceeded` / `guard_rejected` / `not_a_diff`
- **前端必须能区分三态**：`PatchSource = 'llm' | 'template' | 'validate_failed'`
  - `frontend/src/modules/vuln/PatchSection.tsx:9-13`：**绿 / 蓝 / 红**，注释写「**绝不能长成一个样子**」

## 原理 5 · 报多与漏，代价不对称

### 规矩

在拿不准的时候，**选择漏报，而不是误报**。而且要**把偏向写下来**。

### 为什么

`analysis/__init__.py:36-52` 有一张 **11 行的已知精度边界表**，
每行带一个"方向"列，明确标注这个边界是**"漏"**还是**"报多"**。

表下有一句：

> **「报多」与「漏」在安全工具里代价不对称。**

**为什么不对称**：
- **报多** → 用户要花时间逐条核 → 浪费时间，但**不会漏掉真问题**
- **漏** → **用户永远不知道自己漏了什么** → 这是不可恢复的

所以默认偏向"报多"。但**"报多"也不是免费的** ——
误报太多用户就不看了，那时"报多"等于"全漏"。所以才要有第四态 `potential`
把"我怀疑但没证明"单独拎出来。

### 代码里的落点

`verify/context.py` 文件头写的原则更极端：**宁可漏报，不可误拒**。

> 因为"漏"会在别处（静态分析的 `unverified` 清单里）留痕，
> 而"误拒"是**主动把结论说反**。

### 不守会出什么事（真实事故）

`test_verify_absence.py` 的 docstring 记了一次：

> 两条真 SQL 注入因参数名推导错被打成 `rejected`，
> 「**三个环节每步都对，结论是错的**」。

以及精读 3 里那个 `SELECT *` 列数返回 1 的故事 ——
一个曾经"歪打正着"的近似值，在一处看起来无关的改动之后，
**让真注入变成了 `rejected`**。

## 原理 6 · 不确定的事，要显式表达"不确定"

### 规矩

不要用一个具体值去表示"不知道"。**要给"不知道"一个自己的表示。**

### 为什么

看精读 3 那个 bug 的完整因果链：

```
用 1 表示"SELECT * 的列数"
  → 这个 1 曾经是安全的（因为另一处的巧合）
  → 巧合消失（载荷改成按 columns 构造）
  → 1 被当成真值使用
  → 真注入被判 rejected
```

**根因不是"1 选错了"，是"用一个普通值承担了'不知道'的语义"。**
这种编码方式的问题在于：它**在大部分时候都能工作**，
所以不会被发现，直到某个前提变化。

### 代码里的落点

这个规矩在项目里出现**很多次**，都是同一个形状：

| 位置 | "不知道"怎么表示 |
|---|---|
| `context.py:195` | `_column_count` 返回 `int \| None`；`SELECT *` 返回 `None` |
| `analysis` 的 `unexpanded` 标记 | 跨函数调用没展开时，**显式标注**而不是假装算完了 |
| `report/types.py` 的 `degraded` 列表 | 报告哪几项是降级来的，逐项登记 |
| `DetectionMethod` 的保守回退 | 认不出检测方法时落到最保守的 `PATTERN`（`code_audit.py:242-249`）|
| 攻击链的 `verified` / `inferred` | 哪几环实测、哪几环推演 |

**最后一个是这个规矩最重要的应用**，值得单独讲：

> 攻击链最后一环（上传 WebShell → 宿主机 RCE）是**推演**的。
> 系统没有把它标成"已确认"，而是标成 `inferred`，
> 并在报告里写明「第 1–2 环已无害验证，第 3 环由已证实的前置条件推演得出，**未实际执行**」。

### 一个正面的反例（说明这个规矩没被滥用）

`code_audit.py:242-249` 有一个**刻意不保守**的地方：

> `_detection_method`……用 `DetectionMethod(...)` 转一次，转不了就落到最保守的 `PATTERN`…
> 反过来……是在**高估**证据强度，那个方向不能走。

即：**认不出就往下调，不能往上调**。"不确定"在这里必须解析为**更弱的证据**，
而不是更强的。

## 原理 7 · 文档会过期，而且过期不报错

### 规矩

**文档里声称的 ≠ 代码里真有的。** 关键事实去代码里核。

### 为什么

文档过期**不会有任何提示**。代码改了、文档没改，两者看起来都正常，
直到有人照着文档做了一个错的决定。

### 证据（这个项目里的实例，都是本次核实出来的）

| 文档说 | 代码里实际是 |
|---|---|
| `.claude/skills/dev-backend/SKILL.md` 写密码用 `pwdlib[argon2]` | **bcrypt + SHA-256 预哈希**（`core/security.py:18,26-32`）—— 那份 skill 其实是**另一个项目**的模板 |
| `PRD.md:857-858` 示例输出写"误报 2" | 实测**误报 0**（`ranges/README.md:134` 也没附和那个 2） |
| `PRD.md:811` 说文件上传路由是 `/admin/upload` | 实际主路由是 `/api/upload`（`ranges/ecommerce/app.py:133`），`/admin/upload` 只是别名 |
| `PRD.md` 说登录绕过漏洞在 `app.py` | **sink 在 `admin_login.py:43`**（`GROUND_TRUTH.yaml:86-90` 解释了为什么故意这样设计） |
| `assessments.py:378-379` 的 SSE 注释写"池子只有 5 个" | 配置默认是 **2**（`core/config.py:60`） |
| `schemas/common.py` 提到信封 | 本项目**刻意不用** `{code,message,data}` 信封 |

**最后一条尤其值得说**：`frontend/scripts/smoke.mjs` 里曾经有一句注释写
「后端有统一响应信封 `{code, message, data}`」—— 那是**顺着国内后端习惯想当然写的**，
与项目实际设计相反。这类"凭印象写的注释"比过期的文档更危险，
因为它看起来像是有依据的（就写在代码里）。

### 落点

这个项目的做法是：**把关键约束变成测试**。

- `test_import_integrity.py` —— 用 AST 扫所有 `from app.X import Y`，逐个验 `Y` 真的存在
- `test_taint_determinism.py` —— 验 `analysis/` 没有越界 import
- `test_analysis_language_gate.py` —— 钉两套语言词汇表的漂移

**为什么是这三个**：因为这三个问题是**不会报错的**（见原理 8）。

## 原理 8 · 最坏的失败是"静默失败"

### 规矩

**宁可响亮地失败，也不要安静地给出一个错的结果。**

### 为什么

看这次核出来的四个真实事故，**它们的共同点不是"有 bug"，
而是"bug 不产生任何错误信号"**：

| 事故 | 症状 | 为什么没被发现 |
|---|---|---|
| `engine.py` import 了一个**从不存在的** `get_sandbox`（`test_import_integrity.py:1-27` 记录） | `poc_verify` **永远静默降级** | 惰性 import 失败被 except 吞了 |
| `"Python"` vs `"python"` 大小写漂移（`test_analysis_language_gate.py:15-22`） | `files_scanned=0, findings=0`，报告说"**0 个漏洞**" | 阶段状态是 `completed`，一切正常 |
| `Finding` 没带真实主键 → `_vuln_id` 退化成 0（`test_poc_verify_id_seam.py:1-23`） | 探针跑了但全 `unverified` | **阶段状态仍是 `completed`** |
| `_has_shell_true` 恒为 False（精读 2） | 五类命令注入一条不报 | `os.system` 的正例仍然是绿的 |

**第二个是"本系统最坏的失败模式"** —— 这句话是测试自己的 docstring 写的。

**"报告说 0 个漏洞"** 是所有失败模式里最坏的一种：
用户看到一份干净的、格式精美的、状态是"已完成"的报告，
然后**放心地不去修任何东西**。

### 落点

- **`poc_verify` 失败标 `skipped` 而不是"没漏洞"** —— 状态本身就承载了"我没验"这个信息
- **报告里的四态分开措辞** —— `verified` / `potential` / `rejected` / `unverified`
- **`rejected` 的中文措辞被改过**（`report/types.py:66-77`）：
  > 原先是「已复核排除」，而**没有任何人工复核发生在这一步**……
  > 报告的措辞若说「人工已排除」，读者就不会去复核它 ——
  > **这正是假阴性得以存活的方式。**

  现在写的是「**动态未复现（机器判定，待人工确认）**」。

  **这个改动很小，但它体现的东西很大**：一句话的措辞，
  决定了用户会不会去做那个人工复核。

### 一条可操作的判据

测试文件里反复出现的一个写法值得学：**给守卫本身加一个阴性对照**。

`test_import_integrity.py:127-134` 会给测试本身验一次
「确定不存在的名字 → 应该返回 False」。
**没有这个对照，一个"永远返回 True"的守卫会让所有测试变绿** ——
而它什么都没检查。

## 原理 9 · 基础设施约束会倒逼应用配置

### 规矩

配置里的数字要有**出处**，而且那个出处可能是**别人的限制**，不是你的需求。

### 两个实例

**（一）连接池取 2 不是 5**（`core/config.py:45-60`）

> 连接池大小。**默认值由 SSH 隧道的通道上限决定，不是由数据库决定的。**
> ……ECS 的 sshd `MaxSessions` 默认 **10，且按"通道"计而不是按"客户端"计**。

实际症状：取 5 时健康检查在 19 秒后开始返回 500，连接堆在 `CLOSE_WAIT`。
而 **`pool_pre_ping` 救不了半开的通道** —— 它只能在借出连接时探测，
而探测本身也要走通道。

**（二）隧道超限时不能 `invalidate()`**（`deploy/tunnel.py:139-143`）

> 那条连接上**其它健康的通道正被别处用着**，把它关掉等于让一次超限变成一次全面断连。

改成"满了就新开一条连接"，以及"开通道失败要 `retire` 而非关连接"。

### 为什么值得讲

这两条都不是"应用设计"，是**环境逼出来的**。
面试里能讲清这种约束，说明你真的把系统跑起来过，
而不是在纸上画了一个架构。

**同类的还有**：`deploy/tunnel.py:24-31` 的 `direct-tcpip` vs `request_port_forward` ——
「两者名字很像，用错了报的是 `TCP forwarding request denied`……
**错误信息指向的排查方向完全是歪的**」。

## 原理 10 · 量具不能改

### 规矩

**`ranges/` 里的源码是"尺子"，改它等于改刻度。**
要改，必须同一轮同步更新 `GROUND_TRUTH.yaml` 的行号。

### 不守会出什么事（真实事故，有量化记录）

`ranges/README.md:78-96` 记的：

> 给 `ranges/ecommerce/app.py` 的 docstring 补了 5 行说明，
> 召回率从 **11/11 掉到 3/11、误报 8**。**代码一行没改，坏的是基准。**
> （修法是让那次编辑**净增 0 行**，改完行号仍精确落在 88 / 114。）

**注意"代码一行没改，坏的是基准"这句** —— 这是整件事的核心。
系统表现"变差了"，但**被测对象没变，变的是尺子**。

而 `LINE_WINDOW = 2`（`backend/tests/benchmark.py:59`）意味着
**净增 3 行就能让后面所有基准条目失配**。

### 为什么值得单独列一条

因为它是一个**关于"评测体系本身也会骗人"**的教训。
面试里聊到"你怎么衡量效果"时，这个故事能说明：
你不但知道要评测，还知道**评测本身会坏**。

## 附：把 10 条原理压缩成一句话

> **凡是"看不太出来"的地方，都要想办法让它变得看得出来** ——
> 架构边界变成 AST 测试，状态表达变成枚举，不确定变成 `None`，
> 降级变成字段，量具变成版本化的行号。
>
> 因为**在这个项目里，最贵的 bug 全都不会报错**。
