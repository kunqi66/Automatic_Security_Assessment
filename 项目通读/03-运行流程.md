# 03 · 运行流程

五条主线。每条都按「**一步一行 → 这一步在哪个文件 → 不干这步会怎样**」写。

> 最后一栏是重点。**"不做会怎样"才是设计意图**，只说"做了什么"面试官会追问到底。

---

## 主线 1：一次评估，从点按钮到出报告

### 1.1 起点：创建评估

| # | 发生什么 | 在哪 | 不干这步会怎样 |
|---|---|---|---|
| 1 | 前端 POST `/assessments` | `api/v1/assessments.py:160` | — |
| 2 | **独立校验权限** `assessment:create` | `assessments.py:47`（`AssessmentCreator`） | 仅靠前端隐藏按钮 = 越权。**每个写接口都要自己校验**，这是硬约束 |
| 3 | 落一行 `assessments`，`status=created` | — | 不落库就没法断点续跑，进程一挂全丢 |
| 4 | 投递任务 ID 到 Redis Stream | `orchestrator/queue.py` | 不用 Celery（理由见 [01-这是什么.md](01-这是什么.md) §五①） |

> **为什么状态先是 `created` 而不是直接 `running`？**
> 因为投递和消费是两个进程。中间这段窗口里任务"已创建但还没被拿走"，
> 必须有一个状态能表达它，否则重启后无法判断哪些任务需要重新入队。

### 1.2 worker 消费：五阶段主循环

入口 `orchestrator/engine.py`。**并发恒为 1**（2 vCPU，并发只会撞 OOM）。

```
for stage in STAGE_ORDER:          # engine.py
    if 取消标志位已置位:            # engine.py:216-220 ← 协作式取消
        break
    try:
        await agent.run(...)
    except:
        按 agent.fault_tolerance 决定 → FATAL 则整个 failed / SKIPPABLE 则标 skipped 继续
```

| 阶段 | 做什么 | 失败后果 | **为什么是这个级别** |
|---|---|---|---|
| `recon` | 识别语言、入口文件、依赖清单 | **致命** | 认不出技术栈，后面全都无从谈起 |
| `code_audit` | tree-sitter 污点分析 | **致命** | 没有漏洞集合，报告是空的 —— 而"空报告"会被误读成"这个项目很安全" |
| `poc_verify` | 容器里发无害探针 | **可跳过** | 验不了 ≠ 没问题。见下方 ⚠️ |
| `exploit_chain` | 规则引擎串攻击链 | **可跳过** | 同上 |
| `report_gen` | 从数据库快照汇编报告 | **致命** | 这是交付物本身 |

> ⚠️ **第 3、4 步失败为什么能继续 —— 这是本流程最值得讲的一个决定**：
>
> 因为**沙箱连不上就不出报告，等于把"基础设施故障"变成了"这个项目很安全"**。
> 那是最糟的一种错：用户拿到一份干净的报告，而他以为那是结论。
>
> 所以宁可出一份"有 5 条疑似、但一条都没能验证"的报告，
> 也不要因为验证环节挂了就整个失败。

**每阶段产出都落库**（含快照），所以支持**断点续跑** ——
`assessment_stages` 表就是为此存在的。

### 1.3 漏洞状态是怎么定下来的（全程只写一次）

这是 **L1「不参与判定」最硬的一处落点**：

| 什么时候 | 写成什么状态 | 在哪 |
|---|---|---|
| 静态扫到 | `unverified` | `agents/code_audit.py:181`（**写死**） |
| 动态验证完 | `verified` / `rejected` / `potential` | `agents/poc_verify.py:205` |

> **`vulnerabilities.status` 全项目只有这两个写入方。**
> `poc_verify.py:203-204` 的注释写死了：「**`status` 由 B5 判定，这里只搬运**……
> 那正是 L1 要挡的东西。」
>
> 面试可以这么答：**"状态字段的写入点只有两个，都在确定性代码里。
> LLM 那四个用点写的是 `description`、`diff_content`、`narrative`、`note` —— 四个纯文本列。
> 想让模型影响状态，得先改 `llm/types.py` 的类型定义。"**

### 1.4 最后一步：报告汇编

`agents/report_gen.py`（210 行）→ `report/assembler.py`（782 行）。

1. **排序由纯函数算**：`assembler.py:203` `ordered = sorted(rows, key=scoring.chapter3_sort_key)`
   → `:224` `ranked = scoring.rank_recommendations(rows)`
2. **四个表达点在这里被填文本**：
   - 漏洞描述 → `report_gen.py:135` 写 `row.description`
   - 链叙事 → `assembler.py:552` 写 `ChainEntry.narrative`
   - 整改建议 → `assembler.py:602` 写 `Recommendation.note`
3. **渲染 HTML + Markdown 落盘**（同步）；**PDF 不生成**（惰性，见主线 5）
4. 若 LLM 降级过 → `report_gen.py:162-169` 发一条 **WARN 级**日志：
   「报告部分内容为模板生成（LLM 不可用或输出未通过校验）」

> `report/scoring.py:1-6` 的头注把这条界划得很干脆：
> 「**全部是纯函数，没有一行 LLM**……项目综合等级、`security_score`、第 3 章清单顺序、
> **第 5 章的整改顺序** —— 全部由这里的确定性公式产出。
> LLM 只写第 5 章的文案，**既不打分、也不排序**。」

## 主线 2：登录与鉴权

```
POST /auth/login  {username, password}
  → 查 user（bcrypt 校验）           core/security.py:42
  → 签 JWT（HS256，8 小时）           core/security.py:72
  → 写审计日志 auth.login             api/v1/auth.py:38-44
  → 返回 {access_token, token_type, user}

后续每个请求：
  Authorization: Bearer <jwt>
  → decode_access_token              deps.py:105
  → user_id = int(payload.sub)       deps.py:108
  → 回库重取 User                     deps.py:112   ← 关键
  → require(Permission.X) 检查角色    deps.py:123-138→ 403
```

**三个必须能讲的点**：

| 点 | 为什么 |
|---|---|
| **回库重取，不信 token 里的 role** | token 里虽然也签了 role，但**改权限后旧 token 不会失效**。回库重取让权限变更立即生效 |
| **身份绝不从请求体取** | 全库 grep `user_context` / `body["role"]` —— 唯一命中是 `deps.py:4` 那句注释本身。**方向是反的**：`auth.py:48` 是"从库里的 user 写进 token" |
| **每个写接口独立挂权限依赖** | 5 个模块各自 `Annotated[User, Depends(require(...))]`，不共用一个"大网关" |

**密码为什么是 bcrypt + SHA-256 预哈希**（`security.py:5-8` 原文）：
> bcrypt 只看前 72 字节……先做一次 SHA-256 再 base64，把任意长度口令压成固定 44 字节。
> 这就是常说的 **bcrypt-sha256** 方案。

**不干这步会怎样**：不预哈希 → 超过 72 字节的密码，**第 73 字节起被静默忽略**——
两个不同的长密码会被判为同一个。这是个不会报错的漏洞。

## 主线 3：实时日志（SSE）

```
后端：评估过程中不断把日志写进 Redis Stream
    → GET /assessments/{id}/logs （SSE）
    → 读 Last-Event-ID 请求头      assessments.py:308
    → 从该 ID 之后补读（断线重连不丢）  assessments.py:317-322
    → 用独立的短会话，不用请求级会话   assessments.py:377-379

前端：useLogStream.ts
    → fetch + ReadableStream 手动解析（**不用 EventSource**）
    → 游标在过滤之前推进（:150-153）
    → 断了就指数退避重连，最多 10 次（:166-171）
```

**两个"为什么"，都能讲很久**：

1. **为什么不用 `EventSource`**（`useLogStream.ts:4-6` 原文）：
   > 它无法设置请求头，只能把 JWT 塞进 URL 查询串，
   > 而查询串会被 nginx access log、浏览器历史、Referer 记录 —— **等于泄露凭证**。

2. **为什么 SSE 要用独立的数据库会话**（`assessments.py:377-379`）：
   > SSE 连接可以持续几十分钟，把会话挂在这条流上等于**让一个数据库连接被长期占用**。

   > ⚠️ 这段注释里写「池子只有 5 个」，而配置里默认是 **2**（`core/config.py:60`）。
   > **注释过期了**，以 `config.py` 为准。面试若被追问池子大小，答 2 并说明原因（见主线 4 末）。

**不干这步会怎样**：
不传 `Last-Event-ID` → 断线重连后**中间那段日志永久丢失**，用户看到的是跳跃的日志流，
而**没有任何提示**说明丢了东西。

## 主线 4：动态验证（整条链路最"物理"的一段）

```
1. 起容器       sandbox/service.py:105   经 SSH 连远端 ECS 的 Docker
               network_disabled=True     ← 断网，无出口
2. 挂源码       只读挂载
3. 起靶场       容器内把被测应用跑起来
4. 造探针       verify/probe.py          漏洞类型 → 探针模板
               埋一个随机串 nonce
5. 发探针       对准可疑端点发请求
6. 看响应       响应里有没有回显 nonce？
               有 → verified（逐点确认）
               无但风险模式在 → potential（仅类别级）
               被证伪 → rejected
7. 销毁容器
```

**四态为什么要分这么细**（这是设计的核心价值）：

| 状态 | 含义 | 报告里的措辞 |
|---|---|---|
| `verified` | 就是你看到的这一行被跑通了 | "已复现，证据如下" |
| `potential` | 这类问题在本目标上确实存在，但**没证明是你那一行** | "存在风险模式，未获动态确认" |
| `rejected` | 被动态证伪 | 从清单里剔除 |
| `unverified` | 还没走到验证那一步 | 明确标注 |

> **`verified` 和 `potential` 分开的意义**：
> 把"类别级"说成"你这行有问题"，是安全工具最常见的**过度归因**。
> 用户拿着这种报告去改代码，改完发现没解决 —— 信任就没了。

**容器为什么必须断网**：`network_disabled=True` 是**硬约束**，
所以容器里**不能 `pip install`**，一切依赖必须预先打进镜像。

**不干这步会怎样**：
不断网 → 被测代码里若含反弹 Shell 或数据外传，**会在真实网络里执行**。
这不是理论风险 —— 扫描器扫到恶意代码时自己被反杀，是真实发生过的事故类型。

### 一段必须知道的"未完成"

- **探针模板里写死了靶场的路由**（`probe.py`）。所以面对一个真实工程，
  探针很可能**打不中任何端点** → 结果全是 `potential`。
- `runner.py:374` 有个更微妙的问题：**"命中但非本条端点"** ——
  探针在 A 端点拿到了回显，于是判定 B 端点（同一类漏洞）也成立。
  在靶场上这个近似是可接受的，在真实工程上就是**误报来源**。

> 这两条是**已知缺陷**，不是"还没写完"。主动讲出来比被问出来好得多。

### 顺带：连接池为什么是 2

`core/config.py:45-60` 原文：

> 连接池大小。**默认值由 SSH 隧道的通道上限决定，不是由数据库决定的。**
> ……ECS 的 sshd `MaxSessions` 默认 **10，且按"通道"计而不是按"客户端"计** ——
> 每条经隧道的 MySQL 连接占一条通道，**API 与 worker 共享这 10 条**。
> 取 5 时一个进程的上限是 `pool_size(5) + max_overflow(5) = 10`，一个进程就能吃满全部通道；
> 两个进程一起跑必然超限。

**实际症状**：取 5 时健康检查在 19 秒后开始返回 500，连接堆在 `CLOSE_WAIT`。
而 `pool_pre_ping` **救不了半开的通道** —— 它只能在借出连接时探测，
探测本身也要走通道。

**不干这步会怎样**：这是个纯粹的**基础设施约束倒逼应用配置**的例子。
面试里能讲清"为什么是 2 不是 5"，比讲十个设计模式都值钱。

## 主线 5：报告的三种格式与惰性生成

```
评估结束时：只生成 HTML + Markdown        exporter.py:43  formats=(HTML, MD)
                                          assembler.py:337-339 注释说明 PDF 惰性

用户点导出 PDF：
    report/service.py:117   if fmt == PDF: _export_pdf(...)
    → service.py:152
    → exporter.py:78  export_pdf
    → pdf.py:101  render_pdf  ← 起一次 Chromium
    → 超时 20s，重试 2 次       PDF_TIMEOUT_MS = 20_000 / pdf.py:110
```

**为什么 PDF 要惰性**（`pdf.py:5-8` 原文）：
> PDF 是三者里最慢的一步（起一次 Chromium）……把它放进关键路径，
> 等于让「报告生成 ≤30s」这个硬指标去**赌 Chromium 的启动速度**。

**PDF 失败会怎样**（三格式的"可降级程度"是**不一样的**）：

| 格式 | 失败时 | 为什么 |
|---|---|---|
| HTML | 抛错，评估标失败 | 写不进去说明磁盘/权限有问题 |
| Markdown | 抛错，评估标失败 | 同上 |
| **PDF** | **降级**：标记失败但**不抛异常** | PDF 只是个"好看"的格式，不该因为它毁掉整份报告 |

`exporter.py:90-103` 捕获 `PdfUnavailableError` / `PdfRenderTimeoutError`
→ `mark_failed(...)` → 返回 `ExportResult(degraded=True, message=...)`。

**一个很值得讲的踩坑**（`pdf.py:39-47` 原文）：

> ⚠️ **这个超时不能交给 `page.pdf()`**
> ……传进去会直接抛 `TypeError`
> ……所以超时由 `asyncio.wait_for` 在**外层**兜。

> 意思是：Playwright 的 `page.pdf()` **不接受 `timeout` 参数**（那是 `page.click()` 之类的参数）。
> 想当然地传进去，会在运行到那一步时抛 `TypeError` —— 而且**只有在真的导出 PDF 时才暴露**，
> 单测和类型检查都发现不了（Playwright 是动态语言绑定的）。

**前端那条路**（本次刚修好，值得作为一个"集成 bug"的例子讲）：

```
点导出按钮
  ① await reportApi.export(id, fmt)     ← 让后端生成
  ② await reportApi.download(id, fmt)   ← 再把字节取回来
  ③ saveBlob(blob, filename)            ← 落盘
```

> **②原先不存在。** 于是按钮点了之后：后端确实生成了、也返回了成功，
> 但前端**只弹了一句"服务端路径"** —— 用户什么都拿不到。
>
> 更麻烦的是：**四项页面巡检全绿**。因为列表页正常、字符数正常、没有异常。
> 这类"链路断在最后一米"的 bug，只有**真的点进去**才能发现。
> 这也是 `frontend/scripts/smoke.mjs` 后来加了第 5 项检查的原因。
