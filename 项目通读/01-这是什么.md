# 01 · 这是什么

## 一、外行版（讲给完全不懂安全的人听）

假设你写了一个网站，想知道它有没有安全漏洞。

传统做法有两种，都不好使：

- **请人来看代码**（代码审计）：慢、贵、靠人 experienced，而且人会累。
- **用扫描工具扫**：快，但**报一大堆**，里面有真有问题、也有瞎报的。
  你得一条一条去核，最后发现大部分时间花在"排除假警报"上。

**这个系统想解决的就是最后那件事** ——
它先用工具把可疑的地方全找出来（这一步会报多），
然后**真的把代码跑起来，发一条无害的探测请求去试**：

- 试出来了 → 这条**确认**是真的，附上请求和响应的原始报文当证据。
- 试了没反应，但那段代码看起来确实有风险 → 标成"**可能有问题**"，**并且明确说清"我没能证明"**。
- 试了发现根本没问题 → 标成"**误报**"，剔掉。

最后给你一份报告：哪些确认了、哪些只是怀疑、攻击者可能怎么串起来打、以及怎么修。

**它最重要的一个特点**：报告里的判断（有没有漏洞、几级、什么状态、先修哪个）
**不是大模型说的**，是代码算出来的。大模型只负责把结论写成通顺的中文。
所以同一份代码跑两遍，**结论一模一样**，不会今天说有、明天说没有。

## 二、能演示给谁看

需求文档（`需求.md:90-94`）要求做两个场景，这个项目**两个靶场都做了**：

| 靶场 | 模拟什么 | 埋了什么漏洞 |
|---|---|---|
| `ranges/ecommerce` | 电商后台 | SQL 注入、文件上传、路径穿越、反序列化、硬编码密钥 |
| `ranges/usercenter` | 企业用户中心 | 越权（IDOR）、未授权访问、敏感信息泄露、硬编码密钥 |

**"靶场"是什么**：一个**故意写满漏洞的小网站**，专门用来当考试的"标准答案"。
两个加起来 787 行 Python，每个漏洞在 `GROUND_TRUTH.yaml` 里钉死了**文件 + 行号**，
所以系统扫完可以自动对答案 —— 这是这个项目区别于"玩具 demo"的地方（详见 [06-知识点精讲.md](06-知识点精讲.md) 卡片 11）。

**演示链路**（跑一次大概几十秒）：
1. 在概览大盘新建评估，选一个靶场；
2. 工作台看五个阶段一格一格点亮，右边日志在滚；
3. 漏洞列表里点开一条 → 看污点从哪一行流到哪一行、PoC 的请求/响应、AI 生成的修复补丁 Diff；
4. 拓扑图看攻击链（注入 → 拿到凭证 → 上传 WebShell → 拿下宿主机）；
5. 报告中心预览全文 → 导出 PDF / HTML / Markdown。

> ⚠️ 演示前必看：**第 4 步的攻击链最后一环是"推演"不是"实测"**，
> 前端会用两种颜色区分。这是**刻意的**，面试时被问到要能讲清楚（见 [07-面试题库.md](07-面试题库.md) 必答题 3）。

## 三、一句话 / 一分钟 / 三分钟

**一句话**（外行版）：
> 一个自动检查代码安全漏洞的系统，它会**真的把代码跑起来试一下**来确认漏洞是真的，
> 而且**最终结论由确定性代码算出，不由 AI 决定**。

**一分钟**（技术版）：
> 面向源码工程的自动化安全评估系统。五阶段流水线：环境侦察 → tree-sitter 静态污点分析 →
> 在**断网容器**里发**无害探针**做动态验证 → 规则引擎拼攻击链 → 报告汇编。
> 核心设计是**可控多智能体**：漏洞的有无、严重度、CVSS、状态、攻击链的节点与边、
> 整改顺序**全部由确定性代码产出**，LLM 只出现在四个表达点（描述/补丁/叙事/整改建议），
> 全部可降级为模板 —— **拿掉 LLM，结论一字不变，只有措辞变**。
> 后端 FastAPI + SQLAlchemy 异步 + MySQL + Redis Stream，前端 React + AntD + React Flow，
> 沙箱是远程 Docker over SSH，容器 `network_disabled=True`。

**三分钟**：在"一分钟"基础上加三段 ——
① 为什么要有动态验证这一步（静态扫描误报率高，逐条人工核太贵）；
② 无害化红线（攻击链最后一环只推演不执行，`verified`/`inferred` 两态）；
③ 评测体系（两个靶场 + GROUND_TRUTH 逐行钉死 + benchmark 算出 87.5% 召回 / 0 误报）。

（完整口述稿在 [07-面试题库.md](07-面试题库.md) 必答题 1）

## 五、三个"不走寻常路"的选择（面试高频）

### ① 为什么不用 Celery（任务队列的事实标准）

原文（`orchestrator/queue.py:3-8`）：

> Celery 的价值在于多进程并行与跨机器分发，而本系统的并发度**恒为 1** ——
> 2 vCPU 加一个常驻 Milvus，并发只会撞 OOM。
> 引入 Celery 意味着一个 broker 抽象、一套 worker 生命周期、一份序列化协议，
> **换来的能力一条也用不上。**

而且它诚实写了代价：**「重试与死信要自己写。下面 `_handle_failure` 那段就是那个代价。」**

### ② 为什么不用 `asyncio.Task.cancel()` 来"停止评估"

原文（`orchestrator/cancel.py:3-6`）：

> 它会在**任意** `await` 点抛出 `CancelledError`，而阶段执行里有大量 await
> 落在数据库事务中间。恰好在那里被中断的后果是
> 「`Finding` 提交了、它的 `TaintPath` 没提交」—— **孤儿记录**。

所以用**协作式取消**：写一个 Redis 标志位，引擎在**阶段边界**主动检查
（`engine.py:216-220`）。代价是长命令要等它自己超时，但**不会切断事务**。

### ③ 为什么成功响应**不套** `{code, message, data}` 信封

这个反直觉 —— 国内后端习惯统一信封。原文（`schemas/common.py:27-29`）：

> 本系统**不使用** `{code, message, data}` 信封 —— 成功直接返回资源 JSON。
> 理由：信封会让「**哪一层负责剥壳**」变成每个调用点各自判断的事。

（失败响应才是有结构的：`{detail, error:{stage, error_code, message, remediation, ...}}`）

## 六、这个项目**故意不做**什么

理解设计意图最快的入口，是看它明确划掉的边界：

| 不做 | 理由（原文位置） |
|---|---|
| **不执行有副作用的攻击载荷** | 攻击链最后一环推演而非实测；"真的执行 RCE"这个方案被明确否决（`概要设计总纲.md:760`） |
| **不让 LLM 参与任何判断** | 判据：拿掉 LLM 结论一字不变（`概要设计总纲.md:632`） |
| **不做多进程并发** | 2 vCPU 是硬约束（`概要设计总纲.md:579`） |
| **不上微服务** | "2 vCPU 下多进程是纯负担"（`概要设计总纲.md:681`） |
| **不支持 Python 以外的语言** | 只注册了 python 一种 grammar（`analysis/parser.py:31-33`），**显式报错**而不是静默跳过 |
| **不做跨函数深层分析** | 只展开一层（`analysis/__init__.py:40`），已知会漏 |
| **不给审计日志开写接口** | "等于让被审计者自己填证据"（`api/v1/audit.py:3-5`） |
| **默认不对公网开放** | 若要开放必须同时满足三条：强制登录 + 目标白名单 + 全局限流（`概要设计总纲.md:607`） |
