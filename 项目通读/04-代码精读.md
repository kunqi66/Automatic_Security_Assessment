## 精读 1 · 三类误报的豁免 —— `taint.py:705-735`

**文件**：`backend/app/analysis/taint.py`（污点引擎核心）

### ① 它要解决什么

一个 SAST 引擎最容易犯的错，不是漏报，而是**把正确写法报成漏洞**。
比如这段——**这是标准的安全写法**：

```python
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```

参数化查询，`user_id` 是绑定值，**根本没进 SQL 文本**。
但如果引擎只会看"`execute()` 被调用了、参数里有脏数据"，
它就会把这行报成 SQL 注入 —— 而且是报在**做得最对的那一行**上。

这类误报是不可接受的：用户按报告去改，会发现"我已经写对了啊"，
然后**对整个工具失去信任**。

### ② 逻辑怎么走的（逐行）

```python
def _dangerous_args(spec, node, positional, keywords, ctx) -> tuple[...]:
    """按规则表挑出「危险参数位」，并处理三种豁免。"""
    if spec.param_bindings_exempt and is_parametric_sql(node, ctx.const_table):
        return ()                                    # :722-723
    if spec.requires_shell and not _has_shell_true(node):
        return ()                                    # :724-725
    if spec.requires_unsafe_loader and has_safe_loader(node):
        return ()                                    # :726-727

    if -1 in spec.dangerous_args:
        return (*positional, *keywords.values())     # :729-730  全部参数位都危险
    selected = []
    for index in spec.dangerous_args:                # :732-734  只挑指定的参数位
        if 0 <= index < len(positional):
            selected.append(positional[index])
    return tuple(selected)
```

**三道闸，每道对应一类真实误报**（原 docstring `:714-720`）：

| 豁免 | 挡掉什么误报 |
|---|---|
| `param_bindings_exempt` + `is_parametric_sql` | `execute(sql, params)` 的 `params` 是**绑定值**，不是 SQL 文本 |
| `requires_shell` | `subprocess.run(cmd, shell=False)` —— 安全用法 |
| `requires_unsafe_loader` | `yaml.load(x, Loader=SafeLoader)` —— 安全用法 |

返回**空元组**意味着"这个调用点没有任何危险实参"，于是上层 `_handle_sink`
的循环一次都不进，**不产出漏洞**。

### ③ 最容易看漏的地方

**`return ()` 和 `return None` 在这里是两种完全不同的意思。**

- `return ()` = "**我查过了，没有危险实参**" → 这个 sink 调用点不报
- `return None` 在某些函数里 = "**我判断不了**"

看 `_dangerous_args` 的返回类型是 `tuple[...]`（**不是** `Optional[...]`），
所以它**永远不表达"不知道"**。这个设计是刻意的：
"不知道"要由上层用别的机制表达（比如 `unexpanded` 标记），
不能让一个"空元组"同时承担两种语义 —— 那是最容易写出静默漏报的地方。

**另一个陷阱**：`:729` 的 `if -1 in spec.dangerous_args` —— `-1` 是个**哨兵值**，
表示"这个 sink 的所有参数都危险"（比如 `eval(x)` 只有一个参数）。
规则表里写 `-1` 还是写 `[0]` 效果一样但含义不同，读规则表时要注意。

### ④ 如果让我重写

**现在的问题**：三道豁免是**硬编码的三条 `if`**，加第四类豁免就要改这个函数。
而且它们的**顺序**有隐含语义 —— 第一个 `if` 命中就返回，后面的不再检查。

**我会改成**：把豁免做成规则表上的一个字段（像 `dangerous_args` 一样数据驱动），
每条规则声明自己适用哪些豁免：

```python
for exemption in spec.exemptions:        # 数据驱动，加一类只改 YAML/规则表
    if exemption.matches(node, ctx):
        return ()
```

**但要注意**：豁免顺序改变**可能改变结果**（如果两条豁免对同一节点给出不同结论）。
所以重写时必须补一个测试，断言"豁免之间互不重叠"，
否则数据驱动会把一个能看出来的顺序问题变成一个看不见的问题。

## 精读 2 · 一个恒为 False 的函数 —— `taint.py:738-763`

**这是整个项目最值得讲的一个 bug。** 它不是"少报一条"，是**一整类漏洞静默失效**。

### ① 它要解决什么

命令注入的判定有个前提：`subprocess.run(cmd, shell=True)` 才危险，
`shell=False`（默认值）是安全的 —— 因为不经过 shell，`;`、`|` 都没有特殊含义。

所以引擎需要一个函数：**看这个调用有没有写 `shell=True`**。

### ② 逻辑怎么走的（逐行）

```python
#: tree-sitter-python 里布尔字面量的节点类型。**不是 `boolean`** ——
#: `True` 的节点类型就是 `"true"`，`False` 是 `"false"`（实测确认）。
_TRUE_NODE_TYPES = frozenset({"true", "boolean"})          # :741

def _has_shell_true(node: object) -> bool:
    """`shell=True` —— 只看关键字实参。"""
    value = call_keyword_args(node).get("shell")           # :760
    if value is None:
        return False                                       # :762
    return value.type in _TRUE_NODE_TYPES and value.text == b"True"   # :763
```

**逻辑本身只有三行**：拿到 `shell` 这个关键字实参 → 没有就 False →
有就检查它的**节点类型**和**原始文本**。

**双重检查**（`:763` 同时看 `type` 和 `text`）是刻意的：
只看类型的话，`shell=False` 的节点类型也是 `"false"`（在集合外，安全），
但万一某个版本把两者归成同一个类型，`text == b"True"` 这道兜底能救回来。

### ③ 最容易看漏的地方

**这个函数原先恒为 False。** 原文 docstring（`:747-758`）：

> ⚠️ 原先这里比的是 `value.type == "boolean"`，而 tree-sitter-python 给布尔
> 字面量的节点类型是 **`"true"`** —— 于是这个函数**恒为 False**。
> 后果不是"少报一条"，而是 `requires_shell=True` 的那一类 sink 全部静默失效：
>
>     subprocess.run / call / check_call / check_output / Popen
>
> 五个符号，`shell=True` 的命令注入一条也报不出来。而 `os.system` /
> `os.popen` 不带这个条件，照样能报 —— 所以**测试是绿的**。

**为什么测试是绿的 —— 这段话是整个项目里最值得背下来的一段**（`:754-758`）：

> `test_taint_engine.py` 的正例用的是 `os.system`，反例用的是
> `subprocess.run(..., shell=False)`，而反例"通过"的真实原因不是
> "正确识别出 shell=False"，是"压根没识别 shell 这个参数"。
> **一个因为错误原因而通过的反例，比没有反例更糟 —— 它让人以为这条路径被覆盖了。**

**这就是面试里"你怎么保证测试有效"的标准答案**：
测试通过 ≠ 代码正确。要问的是"**它是为什么通过的**"。
这个项目给出的做法是**变异验证**：故意把判断删掉/改错，看测试会不会红。
`test_taint_engine.py:861-864` 记了同类的第二例（`_has_write_sql` 原本无覆盖，删掉也全绿）。

### ④ 如果让我重写

**现在的问题**：`_TRUE_NODE_TYPES` 是个**字符串字面量集合**，
它和 tree-sitter 的版本绑定。tree-sitter 升级改了节点命名，这里会**再次静默失效**。

**我会改成**：不用节点类型的字符串，改成**求值**。既然要看的是"这个表达式是不是真值"，
那就把节点文本拿出来做白名单判断：

```python
_TRUTHY_TEXT = frozenset({b"True", b"true", b"1"})
return value.text in _TRUTHY_TEXT
```

**理由是**：`text` 是源码原文，**不受 tree-sitter 版本影响** ——
用户写的就是 `True`，不管解析器把它标成什么类型。

**代价**：丢掉"它确实是个布尔字面量"这层保证。
`shell=some_var`（变量）会被 `text` 判为不匹配 → 返回 False → 不报。
但**这本来就是当前的行为**（节点类型也不是 `true`），所以没有退化。

**同时要补的测试**：不能只测 `os.system` 和 `shell=False`，
必须**逐个覆盖五个 `subprocess.*` 符号**，并且每个都要有"`shell=True` 必须报出来"的正例。
现在这个 bug 能活下来，根因就是**正例只用了 `os.system` 一个符号**。

## 精读 3 · 星号的列数是"不知道"，不是 1 —— `context.py:191-224`

**文件**：`backend/app/verify/context.py`

### ① 它要解决什么

动态验证 SQL 注入时，探针要构造一个 UNION 载荷，而 UNION 要求**列数匹配**：

```sql
SELECT id, name FROM products WHERE name = '<注入点>' UNION SELECT 1, 2
                                                                    ↑ 必须和左边列数一样
```

所以探针必须知道**原查询有几列**。
`_column_count` 就是从源码里数：`SELECT` 和 `FROM` 之间的顶层逗号数 + 1。

### ② 逻辑怎么走的（逐行）

```python
_SELECT_STAR_RE = re.compile(r"^[A-Za-z_][A-Za-z0-9_]*\s*\.\s*\*$|^\*$")   # :192

def _column_count(prefix: str) -> int | None:          # :195
    upper = prefix.upper()
    start = upper.find("SELECT")                       # :198
    end = upper.find("FROM")                           # :199
    if start < 0 or end < 0 or end <= start:
        return None                                    # :201   读不出

    between = prefix[start + len("SELECT") : end]      # :202

    if _SELECT_STAR_RE.match(between.strip()):         # :213
        return None                                    # :214   ← 本段的重点

    depth = 0                                          # :217
    commas = 0
    for ch in between:                                 # :219
        if ch == "'":
            depth ^= 1                                 # :221   引号深度翻转
        elif ch == "," and depth == 0:
            commas += 1                                # :223
    return commas + 1
```

**三个细节**：

1. **返回类型是 `int | None`** —— 显式承认"可能读不出来"
2. **引号深度用 `depth ^= 1` 翻转**（而不是计数）——
   SQL 里单引号是成对的，`'a,b'` 里的逗号不算分隔符
3. **`SELECT *` 直接返回 None** —— 这是本段的重点，见下

### ③ 最容易看漏的地方

**`SELECT *` 的列数返回 `None`，而不是 1。** 原文注释（`:203-212`）：

> ⚠️ `SELECT *` / `SELECT t.*` 的列数是**不知道**，不是 1。
>
> 这里返回 1 曾经是安全的 —— 那时载荷恒为两列，`1 != 2` 于是
> `payload_fits_context` 判"不适配"，未命中不构成证伪，歪打正着。
> 载荷改成按 `ctx.columns` 构造之后，1 就**真的会去构造一个一列的载荷**，
> 于是 `1 == 1` 判成适配 —— 一张五列的表上打了单列 UNION，必然不命中，
> **而这次未命中被当成"证伪"，真注入被写成 `rejected`。**

**读三遍这段话。** 它描述的是一个**级联失效**：

```
一个"曾经歪打正着"的近似值（1）
   + 一处看起来无关的改动（载荷改为按 ctx.columns 构造）
   = 真漏洞被判成"已排除"
```

**为什么这个 bug 特别危险**：`rejected` 在报告里是"**已排除**"的意思。
用户看到 `rejected` 会**跳过它**。所以这个 bug 的产物不是"报告里多了条噪音"，
而是"**一条真漏洞从报告里消失了**"。

**这条与 `test_verify_absence.py` 的 docstring 是同一个主题**：
「两条真 SQL 注入因参数名推导错被打成 `rejected`……**三个环节每步都对，结论是错的**」。

> 所以这个模块的文件头写着一条原则：**宁可漏报，不可误拒**。
> 因为"漏"会在别处（静态分析的 `unverified` 清单里）留痕，
> 而"误拒"是**主动把结论说反**。

### ④ 如果让我重写

**现在的问题**：`_column_count` 用正则和手写扫描解析 SQL 片段 ——
它只处理了 `SELECT ... FROM` 这一种形状，遇到子查询、`UNION` 嵌套、
`GROUP BY` 会算错，而且**算错时不会返回 None，会返回一个错的数字**。

**我会改成**：给它加一个"**置信度**"返回值，而不是硬要把 `int | None` 塞满。

```python
@dataclass
class ColumnCount:
    value: int | None
    certain: bool        # 能否确定
```

只有**极其简单**的形状（`SELECT a, b, c FROM ...`，无嵌套）才 `certain=True`；
其他一律 `certain=False`。然后**只有 `certain=True` 时才允许用未命中来证伪**。

**这个改法的意义**：它把"这个数字有多可靠"变成**显式信息**，
让下游的 `payload_fits_context` 能做出"不确定就不要判证伪"的决定。
现在的 `None` 只能表达"完全不知道"，表达不了"大概是 3 但我不确定"。

**代价**：会更保守 —— 一些本来能证伪的 case 变成不能证伪，
`rejected` 的数量会减少。**但按模块自己的原则（宁可漏报不可误拒），这个方向是对的。**

## 精读 4 · `-\n+` 是"替换"不是"删除+新增" —— `patch_guard.py:282-316`

**文件**：`backend/app/verify/patch_guard.py`（749 行，补丁的四道校验）

### ① 它要解决什么

第二道校验是「**只允许改 ±20 行窗口内的代码**」——
因为 LLM 只看到了目标漏洞周围 ±20 行的片段，它可能改的地方**不该超出它看到的范围**。

要判"改了哪几行"，就得解析 unified diff，把每个 `+`/`-` 行映射回**原文件**的行号。

### ② 逻辑怎么走的（逐行）

```python
    touched: list[int] = []                            # :282
    #: 当前这组"改动"（连续的 `-`/`+`）在原文件里的起始行号。
    #:
    #: 为什么需要它：`-\n+` 是**替换**，新增行占据的就是被删掉的那一行在原文件里的
    #: 位置。若按 `old_cursor` 记（删除行已经把它推进了一格），一个恰好落在窗口
    #: 边界上的合法替换会被判成"改到了 ±20 行之外" —— 一次纯属自造的拒绝。
    group_start: int | None = None                     # :288

    while index < len(lines):
        line = lines[index]
        if line.startswith("@@"): break                # :292-293 下一块
        if line.startswith("diff --git ") or line.startswith("--- "): break
        if line.startswith("\\"):                      # :296-298
            index += 1; continue                       #   `\ No newline at end of file`：合法，不计数
        if line.startswith("+"):                       # :299
            touched.append(group_start if group_start is not None else old_cursor)  # :301
            new_seen += 1
        elif line.startswith("-"):                     # :303
            if group_start is None:
                group_start = old_cursor               # :305   记录这组改动的起点
            touched.append(old_cursor)                 # :306
            old_cursor += 1
            old_seen += 1
        elif line.startswith(" "):                     # :309
            group_start = None                         # :310   上下文行结束了上一组改动
            old_cursor += 1
            old_seen += 1; new_seen += 1
        else: break
        index += 1
```

**核心机制是 `group_start`**：遇到第一个 `-` 时记住它在原文件的位置；
随后紧跟的 `+` 行**也用这个位置**（而不是已经推进过的 `old_cursor`）。

### ③ 最容易看漏的地方

**`+` 行的行号映射规则是"它插进来的那一点"，不是"它自己占的行"。**

想象一个替换：

```
@@ -18,1 +18,1 @@
-old_line
+new_line
```

- 遇到 `-`：`group_start = 18`，`touched = [18]`，`old_cursor` 推到 19
- 遇到 `+`：`group_start` 是 18 → `touched = [18, 18]` ✅

**如果用 `old_cursor`**：`touched = [18, 19]` → 若窗口边界正好是 18，
第 19 行就"越界"了 → **一次纯属自造的拒绝**。

**为什么这个细节很重要**：它导致的错误不是"漏报"，而是
**把一份完全合法的补丁判成不通过**，然后把 `PatchSource` 标成 `validate_failed`
（前端**红字告警**）。用户看到的是"AI 生成的补丁有问题"，
而实际上**是校验器自己的 bug**。

**另一个容易漏的**：`:296-298` 的 `\ No newline at end of file` ——
这是 unified diff 的合法标记（表示文件末尾没换行），必须跳过**且不计入行数**。
少这一条，所有"改文件最后一行"的补丁都会因为行数对不上而被拒。

**还有 `:294` 的 `if line.startswith("--- ")`** ——
`---` 既可能是 diff 的文件头，也可能是**被删除的一行内容恰好以 `--` 开头**。
这里用 `--- `（带空格）来区分。这类"元字符与内容撞车"的问题，
在写解析器时是最常见的坑。

### ④ 如果让我重写

**现在的问题**：这个手写解析器**只用在一个很窄的场景**（±20 行窗口检查），
却要正确处理 unified diff 的全部边界情况。项目自己在 `:152-156` 解释了为什么不引库：

> 不用 `unidiff` 之类的库：一是环境里没有、而本模块不许装依赖；
> 二是这里需要的不是"通用 diff 解析"。

**这个理由我认同**（沙箱里不能 `pip install`），但我会补一件事：

**用属性测试（property-based testing）覆盖解析器。** 现在的测试是手写 case，
而手写 case 覆盖不到"`-` 行内容恰好是 `--- `"这种组合。

```python
@given(st.lists(st.sampled_from(["+x", "-y", " z", "\\ No newline"]), min_size=1))
def test_touched_always_within_declared_range(lines):
    # 生成的 diff 里 touched 的行号必须落在块头声明的范围内
```

**理由是**：解析器的 bug 有一个共同特征 —— **在合法输入上返回错误的行号**，
而错误行号的后果（自造拒绝）又和"补丁真的越界"长得一模一样。
用随机输入去撞边界，比手写 case 有效得多。

## 精读 5 · 容错档位为什么不写在引擎里 —— `agents/base.py:1-75`

**文件**：`backend/app/agents/base.py`（161 行，五个 Agent 的共同父类）

### ① 它要解决什么

两件事：

1. **可插拔**：新增第 6 个 Agent，不该去改引擎
2. **容错分级**：`poc_verify` 失败不该拖垮整个评估，但 `code_audit` 失败应该

### ② 逻辑怎么走的（逐行）

```python
class FaultTolerance(StrEnum):                          # :53
    #: 失败 → 整个评估 `failed`。`recon` / `code_audit` / `report_gen` 属此档
    FATAL = "fatal"                                     # :58
    #: 失败 → 阶段标 `skipped`，**后续阶段继续**。`poc_verify` / `exploit_chain` 属此档
    SKIPPABLE = "skippable"                             # :61


@dataclass(frozen=True, slots=True)                     # :64
class AgentDeps:
    """Agent 的运行时依赖。

    `frozen` 是刻意的：这些依赖在阶段执行期间不该被替换。
    `slots` 是为了让「往上面挂一个临时属性」这种写法在运行时直接报错 ——
    它本就是不该发生的事，早失败好过晚失败。
    """
    #: 引擎持有的会话。**Agent 不得 commit** —— 提交点在阶段边界（T4）。
    session: AsyncSession                               # :74
    broadcaster: LogBroadcaster
```

**容错档位挂在 Agent 类上**，引擎只读这个属性 —— 于是引擎里
**没有任何 `if stage is X` 分支**（`:6-8`）。

### ③ 最容易看漏的地方

**`frozen=True, slots=True` 这两个参数不是为了性能。**

- `frozen=True` → 依赖在阶段执行期间**不能被替换**
- `slots=True` → "往上面挂一个临时属性"**在运行时直接报错**

原文（`:68-71`）说得很清楚：「它本就是不该发生的事，**早失败好过晚失败**」。

**这是一个可以举一反三的设计观**：把"不该发生"变成"不可能发生"，
比写一堆注释说"请不要这样做"强。类似的还有 `llm/types.py` 的 `TextResult` ——
**类型里根本没有 severity 字段**，所以"让 LLM 影响严重度"这件事
**得先改类型定义才能做**，而不是"记得不要传"。

**第二个容易漏的点：为什么 `session` 走构造函数注入**（`:21-30`）：

> T4 定的是「阶段边界是唯一原子提交点」—— 阶段内不得提交。所以 Agent 写库
> 必须用**引擎持有的那个 session**，由引擎在阶段结束时统一 commit。
> 如果把 session 塞进 `run` 的参数或者放进 `ctx`……
> 前者改了签名，后者往一个**会被序列化**的载体里塞**不可序列化**的东西。

**"`ctx` 会被序列化"** 是理解整个编排层的一把钥匙 ——
`ctx` 要落库（断点续跑），所以任何放进去的东西都必须可序列化。
一个数据库 session 显然不是。

### ④ 如果让我重写

**现在的问题**：`FaultTolerance` 只有两档。但看 `report/types.py` 和实际代码，
失败其实有**三类**后果：整个评估失败 / 阶段跳过但记警告 / **阶段成功但有降级**。

第三类现在散落在各处（报告里 PDF 降级 `ExportResult(degraded=True)`、
LLM 降级 `degraded` 字段），**没有一个统一的表达**。

**我会改成**：把档位扩成三档，并且让 `AgentResult` 显式带降级信息：

```python
class FaultTolerance(StrEnum):
    FATAL = "fatal"              # 失败 → 整个评估 failed
    SKIPPABLE = "skippable"      # 失败 → 标 skipped，继续
    DEGRADABLE = "degradable"    # 成功，但产出可能不完整（如报告用了模板）
```

**理由是**：现在"这份报告里有内容没通过 LLM 校验"这个事实，
只存在于一条 **WARN 日志**（`report_gen.py:162-169`）和报告里的一个字段里。
如果前端想给用户一个显眼的提示，它得自己去解析报告内容。
把它提到阶段结果上，前端就能直接读。

**但要小心**：`DEGRADABLE` 和 `FATAL` 的边界不能混 ——
"报告用了模板"是降级，"报告根本没生成"是致命。这两件事在 UI 上必须分开说。

## 精读 6 · 拒收，而不是删掉那一句 —— `llm/guard.py:1-35`

**文件**：`backend/app/llm/guard.py`（153 行）

### ① 它要解决什么

LLM 会**编造出看起来很合理的东西**。文件头 `:5-6` 举了真实的例子：

> 模型在温度 0.2 下依然会写出「类似的 `app/api/login.py`」这种看起来很合理的路径，
> 而那种幻觉在安全报告里是最贵的错误：**读者无法分辨哪条位置是真的**。

注意：**温度 0.2 也不能消除幻觉**。这是关键前提。

### ② 逻辑怎么走的（逐行）

```python
"""L3「输出必校验」：实体白名单。

PRD §7.6.2 的 L2 说「LLM 输出中不得出现输入里没有的文件路径、行号、CVE 编号、
函数名、漏洞编码」。**这句话单独写在 prompt 里是没有约束力的** —— ...
所以这里是**硬闸**：从模型输出里把「可被追问的实体」全部抽出来，逐个核对
是否在输入里存在。**任何一条对不上，整段拒收，走确定性模板**（不是删掉那一句 ——
删掉会让文案读起来仍然通顺，从而让幻觉的痕迹消失）。      # :1-10
"""
```

**已实现的五项检查**（`:20-27`）：

| 实体 | 怎么查 |
|---|---|
| 文件路径（带扩展名） | 必须精确命中输入里的 `file_path` 集合 |
| `路径:行号` | 路径命中 + 行号落在该漏洞的 **±20 行**窗口内 |
| 「第 N 行」/「行 N」 | 行号必须在允许集合内 |
| CVE 编号 | 必须命中输入的 CVE 集合 |
| 漏洞编码 `VULN-xxxx-xxxx` | 单条用输入编码；攻击链用**链的节点集合** |
| **函数/符号名** | ⚠️ **未实现** |

### ③ 最容易看漏的地方

**三个，一个比一个重要。**

**（一）"拒收整段"和"删掉那一句"是两回事**（`:9-10`）：

> 不是删掉那一句 —— **删掉会让文案读起来仍然通顺，从而让幻觉的痕迹消失**。

这句话值得停下来想。为什么不能删？

假设模型写了三段，第二段里有个编造的文件路径。删掉那一句之后：

- ✅ 读者看到的是干净的文本
- ❌ **读者不知道这里曾经有过一个幻觉**
- ❌ 剩下的文本**语义可能已经错了**（比如"该问题在 X 和 Y 两处"删掉 X 变成"在 Y 处"）

**拒收整段 + 降级为模板**，代价是措辞变差，但**结果是可解释、可复现的**。

**（二）为什么不"改写"**（`:12-16`）：

> 拒收的代价已知且可控（措辞变差）；改写的代价是「我们发明了一段既不是模型说的、
> 也不是模板说的文本」，它无法解释、无法复现。
> 按 L4，降级是允许的，**发明**是不允许的。

**"降级是允许的，发明是不允许的"** —— 这句话是 L4 的完整表述。
面试里被问"LLM 输出不合格怎么办"，这句话可以直接用。

**（三）函数名为什么故意不查**（`:29-34`）：

> 判断「`run_query` 是不是输入里存在的符号」需要先把自然语言里的标识符切出来，
> 而中文技术文本里 `` `order_id` ``、`cursor.execute`、「订单查询接口」混在一起，
> 规则法切出来的候选**一半是噪声**。噪声的代价是**误拒** ——
> 而误拒会把本来合格的模型输出也推回模板，等于**把用点①③④一起废掉**。
> ……**这是一个已知的、有意的空缺，不是遗漏。**

**这是"知道自己不知道什么"的典范。** 一个未实现项，写清了：
① 为什么难，② 做了会有什么代价，③ 正确的做法是什么（B4 输出符号表），
④ 以及"这是有意的空缺"。

### ④ 如果让我重写

**现在的问题**：五项检查全部是**正则 + 集合查找**，而"实体抽取"这一步
本身就是正则在干。`_PATH_RE` 的注释（`:42-43`）已经承认了这个张力：

> 放宽成 `\w+\.\w+` 会把 `foo.bar` 这种点号表达式也当成路径，噪声大到不可用。

也就是说：**收紧 → 漏检（幻觉混过去）；放宽 → 误拒（好输出被废掉）**。
现在选的是收紧（只认常见源码扩展名）。

**我会改成**：**分层校验 + 分级处置**。

```
第一层（高置信）：路径:行号、CVE、漏洞编码  → 不通过 = 整段拒收（现状）
第二层（低置信）：裸文件路径、「第 N 行」   → 不通过 = 只标注，不拒收
```

**理由是**：现在的"整段拒收"对**所有**五项一视同仁，但五项的误判率差别很大 ——
`路径:行号` 几乎不会误判（有冒号分隔，形状明确），而裸路径很容易误判。
**用一个最严的处置去兜一个最松的检查，等于让误判率最高的那一项决定整体质量。**

**代价**：第二层"只标注"意味着幻觉**可能留在报告里**。
所以必须在 UI 上把标注做得显眼（比如给那句加个"未核实"的角标），
否则就是把一个已知问题藏起来 —— 那比现在更糟。
